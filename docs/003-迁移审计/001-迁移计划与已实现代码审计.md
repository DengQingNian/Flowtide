## 1. 审计结论与证据口径

当前实现已具备可运行的 BPMN 原型和大量功能测试，但**尚不具备直接替换 Java Flowable、承接存量生产数据库的验收证据**。本次优先发现数据恢复缺失、租户身份未绑定和失败命令的持久化不一致；随后才是按表持久化、集群、性能和接口补齐。数据恢复遗漏在审计期间已出现工作区修复并通过针对性复测，尚未作为本报告提交的一部分。

本次构造了 11 个针对正确行为的临时审计测试，全部触发现有缺陷；其中一个测试同时验证模型和实例身份链接，另一个测试同时验证缺省和伪造租户头。现有测试可以全绿而这些断言失败，说明覆盖率不能代替恢复完整性、事务一致性和授权语义验收。

证据分三类，后文逐项标明：

| 标记 | 含义 | 可以据此得出的结论 |
| --- | --- | --- |
| 已复现 | 本地最小测试实际触发错误 | 在所列条件下缺陷成立 |
| 静态确认 | 代码、SQL、文档之间存在可直接核查的矛盾 | 指定路径存在缺口；未宣称做过真实数据库故障演练 |
| 已知限制 | 实施文档已承认、且代码仍未提供的能力 | 应纳入发布边界和退出条件，不等同于新增回归 |

审计开始时工作区已有未提交的 MySQL 接入改动；审计期间这些改动继续变化，包括 `Makefile`、`README.md`、实施文档、命令入口、新增 `internal/persistence/mysql` 与 `go.mod/go.sum`，以及后续的快照遗漏修复。本报告将其作为“工作区 MySQL 首阶段实现”单独说明，避免把在途成果当成已提交基线。下列源代码行号按初始采样版本记录，后续修复可能使行号移动，应结合函数名定位。本次只提交本报告，不纳入其他工作区变更。

没有输出 `.env` 凭据，没有对开发数据库执行 DDL 或数据修改，没有运行 Java 引擎对照。复杂 BPMN 全量语义、安全全量渗透、百万数据性能不在本次已完成验证范围内。

## 2. 迁移工作计划的问题

### 计-01：兼容基线没有形成可执行的版本锁定（P1，静态确认）

证据：[总览](../001-flowable-go-重构计划/001-项目总览与范围界定.md)和 [ADR](../001-flowable-go-重构计划/014-架构决策、风险与验收标准.md)使用 `8.1.0-SNAPSHOT`；DDL 使用 `8.1.0.3`；计划中没有把参考提交、OpenAPI 文件摘要、DDL 摘要、夹具清单绑定成同一版本制品。

影响：同一个“8.1”名义下，表结构、路由和行为可能来自不同提交，兼容测试没有稳定的比较对象。本报告记录的 Java 提交是本次本地观察值，不代表计划已经锁定该提交。

整改：建立版本清单，至少包含 Java 提交、规范文件及校验和、数据库版本、DDL 及校验和、受支持变量类型、BPMN 语料清单和差异白名单。升级任一项时重新执行三层兼容验证。负责人建议：架构负责人、兼容测试负责人。

### 计-02：把“功能重写”与“存量迁移”混为同一个完成口径（P1，静态确认）

证据：总览要求直接读写既有 `ACT_*`，并提供平滑切换；当前 `flowable-migrate` 主要导出或初始化 Schema，未提供存量流程、变量、Java 委托、监听器和脚本的扫描与转换闭环。[MySQL 首阶段计划](../002-迁移实施/052-MySQL集成计划与首阶段实现.md)已明确只支持本工具初始化的数据库和单记录 JSON 快照。

影响：空库部署成功、SQL 快照重启成功，不能证明 Java 创建的运行中实例可以在 Go 中续跑，更不能证明 Go 写入的数据可由 Java 接管。

整改：分别设立“新建库原型”“既有库只读预检”“停写切换续跑”“可回退迁移”四个验收状态。迁移清单必须包含源实例与租户清点、未知变量类型拒绝、委托映射、定时器和订阅处理、转换报告、备份恢复、切换前后核对。负责人建议：迁移负责人、DBA。

### 计-03：实施记录与原始计划已经脱节（P2，静态确认）

证据：[实施进度与差距](../002-迁移实施/002-实施进度与差距.md)的已实现清单已有 Ad-hoc、Send/Receive、重试/死信、批处理、JWT/JWKS，但剩余差距或下一阶段建议仍重复列入这些能力；Ad-hoc 在剩余清单中还重复出现。[MVP 说明](../002-迁移实施/001-MVP实现说明.md)仍建议下一步抽象 `Store`。README 末尾仍称“纯标准库实现”，与在途 MySQL 依赖不一致。

原始计划的 ADR-005 选择 goja/Starlark，实际脚本任务仅实现表达式子集；ADR-010 要求空租户代表默认租户，实际空租户可以跨租户访问，见码-02。范围总览出现 M15/M18，但排期只定义至 M13。这些偏差尚未通过统一状态表收敛。

整改：建立唯一能力矩阵，每项包含计划范围、实现提交、验证方式、限制、责任人和下一验收门槛。状态至少区分“已编码、已单测、已真实数据库验证、已 Java 对照、可发布”。旧文档保留设计意图，但标明实际偏差和替代 ADR。负责人建议：技术负责人。

### 计-04：质量门禁仍是文档目标，未形成自动阻断（P1，静态确认）

证据：[测试计划](../001-flowable-go-重构计划/012-测试策略与质量门禁.md)要求 `covergate`、`.coverignore`、`doccheck`、数据库双库 CI、Java 回放、OpenAPI 校验、关键包 95% 与新增代码 95%。本次盘点未发现对应已跟踪的 CI、`tools/covergate`、`tools/doccheck`、`.coverignore` 或参考语料测试目录。当前 `make cover` 仅打印报告，`make lint` 只执行 `go vet`。

影响：覆盖率不足、真实数据库长期跳过、注释缺失、契约漂移均不会自动阻止提交。现有规范混用“行覆盖率”和 Go 工具的“语句覆盖率”，也没有可执行的增量口径。

整改：先实现最小门禁：格式、vet、普通测试、独立的 race 环境、90% 总语句覆盖率、明确包清单和排除项；再加入按包/增量阈值、中文函数注释检查、数据库与契约任务。数据库任务在显式启用时失败必须判失败，不得转成跳过。负责人建议：QA、DevOps。

### 计-05：接口数量与覆盖率被用作兼容性代理指标（P1，静态确认）

证据：[REST 计划](../001-flowable-go-重构计划/011-REST-API与兼容契约.md)区分 119 个路径和约 184 个方法；实施记录使用“234 个路由”。三者分母不同，无法由数量推导缺失项。计划要求的响应模式验证、Java 回放未落地。`variables-async` 当前同步执行，返回状态类似异步接口，但时序、失败与重试语义不同。

整改：以“HTTP 方法＋规范化路径”为主键列出官方、实现、扩展、缺失和明确不兼容端点；逐项检查输入、响应模式、错误、分页、变量类型和副作用。同步替代异步、表达式替代 JavaScript、子集 DMN 必须标记部分支持。负责人建议：REST 与兼容测试负责人。

### 计-06：发布灰度与数据库回退方案没有实例归属机制（P1，静态确认）

证据：[里程碑计划](../001-flowable-go-重构计划/013-里程碑、排期与资源计划.md)提出 1%→10%→50%→100% 流量灰度和保留旧镜像/Schema 回滚；ADR 又要求禁止双写。现有实现没有跨引擎作业仲裁和实例归属隔离。

影响：仅按 HTTP 流量分配 Java/Go，无法保证任务完成、定时器、消息和后台作业属于同一执行者。镜像回退也不能撤销已经变化的变量编码或不兼容运行状态。

整改：首个生产试点采用受控停写切换，暂停两个引擎的后台执行，完成备份、预检、转换、核对后再启用单一执行者。若需要灰度，按独立租户/实例集合/数据库隔离并落实路由归属；回退前提必须包含 Java 读 Go 数据及续跑验证。负责人建议：迁移负责人、运维。

### 计-07：排期的资源和退出条件未重新估算（P2，静态确认）

证据：013 明列工作量含缓冲 483 人周，6.5 FTE×70 周只有 455 人周，差额 28 人周仍未落实。M2 退出要求覆盖率 85%，与仓库 90% 要求不一致；关键路径图要求 M9 后进入 M10，但时间窗又允许其在 GA 完成前开始。当前大量功能已有代码，M0/M2 的数据库与 CI 门槛却仍缺证据。

整改：不按功能提交数宣布阶段完成。以本报告的阻断项重建依赖图和剩余工作量，明确每阶段输入、责任人、预算、产物和可重复执行的退出命令。先补基础门槛，再重新承诺日期。负责人建议：项目负责人、技术负责人。

## 3. 已实现代码中的问题

### 码-01：快照未保存流程模型和运行时实例身份链接（P0，基线已复现；工作区已修复复测）

- 位置：[snapshot.go](../../internal/engine/snapshot.go) 的 `snapshot`（第 32 行）、`toSnapshot`（第 66 行）、`loadState`（第 173 行）；对照 [state.go](../../internal/engine/state.go) 中 `Models`、`InstanceLinks`。
- 触发：创建模型，启动带 `UserID=alice` 的流程，成功保存并关闭；用相同 `StateStore` 新建引擎。
- 实际：`GetModel` 返回 `ENGINE-1001`；实例身份链接从 1 条变成 0 条。JSON 结构根本没有这两个集合，模型源码也随模型一起丢失。
- 影响：文件快照和 SQL JSON 快照共享同一序列化路径；工作区 MySQL 首阶段接线不会解决这个缺陷。历史身份链接存在也不能替代运行时链接。
- 修复与验收：完整盘点 `state` 每个持久字段，提供版本化快照与升级策略。重启前后比较模型信息/源码、实例身份链接及全部业务集合；重复恢复和后续增删改均应正确。建议责任：持久化负责人。
- 复核补记：文档完成前，工作区 `snapshot.go` 已补入 `Models/InstanceLinks` 的保存与恢复，新增 `TestSnapshotModelAndInstanceLinks`。执行 `go test -count=1 -run 'Test.*(Snapshot|Persist|Model|InstanceIdentity)' ./internal/engine` 通过，其中覆盖模型及两份编辑源、发起人链接的新引擎恢复。此项从“待修复”调整为“工作区修复已复测、待提交及整体验收”；原复现保留为基线缺陷证据。既有快照中从未保存的数据仍需另行恢复。

### 码-02：租户由请求自行选择，JWT 租户不参与授权（P0，已复现）

- 位置：[server.go](../../internal/rest/server.go) 的 `Handler/withTenant`（第 127/134 行）和 `requestTenant`（第 2874 行）；[jwt.go](../../internal/rest/jwt.go) 的 `TenantClaim`；[tenancy.go](../../internal/engine/tenancy.go) 的 `allowTenant`（第 14 行）。
- 触发：签发有效 JWT，声明 `tenant_id=tenant-a`，读取 `tenant-b` 的模型；分别不带租户头、携带 `X-Tenant-Id: tenant-b`。
- 实际：两个请求都返回 HTTP 200。`TenantClaim` 只解析不授权；租户中间件在认证前读取客户端输入；空请求租户直接通过资源校验。
- 影响：不能把“传入不同租户头时会过滤”当成身份隔离。认证有效的普通用户可以选择其他租户或利用空租户读取其他租户资源。
- 修复与验收：认证完成后建立可信身份上下文；租户默认取认证身份，普通用户不得覆盖；跨租户管理员必须显式授权。空租户只代表默认租户。覆盖 GET、写入、查询、管理子资源、消息/信号和不同认证方式。建议责任：安全与引擎负责人。

### 码-03：命令回滚只浅拷贝变量值（P1，已复现）

- 位置：[state.go](../../internal/engine/state.go) 的 `cloneState`（第 232 行）与 `cloneAnyMap`（第 396 行）。
- 触发：变量为 `map[string]any{"obj": map[string]any{"v": "原值"}}`，命令或委托修改内部 `obj.v` 后返回错误。
- 实际：引擎虽然替换为备份状态，`obj.v` 仍为“修改值”。嵌套 map、slice、字节数组等共享底层对象。
- 影响：命令失败后变量已变化；后续成功保存可能将其持久化。部分 DTO 和委托上下文也会暴露共享值，需一并审查读接口的可变引用。
- 修复与验收：对受支持变量类型实施可靠复制或不可变封装；设置、读取、回滚均定义所有权。用嵌套对象、数组和字节数据验证失败后状态与历史不变。建议责任：运行时负责人。

### 码-04：同时配置快照与行仓储时，失败命令已经写入快照（P0，已复现）

- 位置：[engine.go](../../internal/engine/engine.go) 的 `execute`（第 245 行）、`Close`；[snapshot.go](../../internal/engine/snapshot.go) 的 `saveState`；[sql_persist.go](../../internal/engine/sql_persist.go) 的 `persistRows`。
- 触发：配置 `StateStore` 和 `RowRepository`、不启用 `LoadRows`；先成功部署并启动，变量 `n=1`；下一次设置 `n=2` 时让行仓储报错。
- 实际：调用返回错误，内存回滚；重新从 `StateStore` 打开引擎后 `n=2`。写入顺序是快照成功→行仓储失败→只回滚内存。
- 影响：同一命令对调用者失败，对重启恢复却成功；重试可能产生重复副作用。`LoadRows=true` 的单行仓储来源可以避开此路径，但构造配置没有拒绝其他组合。
- 修复与验收：明确唯一权威存储并在构造时拒绝冲突配置；若必须双介质，设计可恢复的一致性协议。故障注入覆盖保存、行事务、提交、关闭和重启；失败命令不得在任一权威恢复路径出现。建议责任：持久化负责人。

### 码-05：数据库修订号增长后没有回写内存基线（P1，已复现）

- 位置：[sql_export.go](../../internal/engine/sql_export.go)、[sql_export_runtime.go](../../internal/engine/sql_export_runtime.go) 多处写死 `REV_=1`；[sql_persist.go](../../internal/engine/sql_persist.go) 第 54 行；[row.go](../../internal/persistence/flowable/row.go) 第 209 行。
- 触发：严格模拟数据库 `WHERE ID_=? AND REV_=?`，创建模型后连续两次更新模型名称。
- 实际：第一次将数据库版本改为 2，但 `lastRows` 仍记录 1；第二次使用旧版本 1，返回 `ROW-0012` 乐观锁冲突。恢复带较高版本的行后也缺乏连续版本维护。
- 测试盲区：现有 `persistTx.ExecContext` 只返回成功行数，没有模拟版本变化。
- 修复与验收：实体或持久化会话持有真实版本，事务成功后才推进基线，失败不推进。验证同一行至少三次连续修改、重启后修改、两个引擎真实竞争、删除与更新竞争。建议责任：行仓储负责人。

### 码-06：PostgreSQL UPDATE 占位符编号错误（P1，已复现）

- 位置：[row.go](../../internal/persistence/flowable/row.go) 的 `UpdateSQL`（第 209 行）。
- 触发：插入列为 `ID_, REV_, NAME_`，跳过 `ID_` 后生成 SET 子句。
- 实际生成：

```sql
UPDATE ACT_RE_MODEL SET REV_ = $2, NAME_ = $3 WHERE ID_ = $3 AND REV_ = $4
```

- 参数却是 `[2, "修改", "m1", 1]`；应为 `REV_=$1, NAME_=$2, ID_=$3, REV_=$4`。当前语句缺 `$1` 且重复 `$3`，参数位置与类型都不正确。
- 修复与验收：按实际追加的参数数编号，校验全部可变列子集；在真实 PostgreSQL 中完成带修订号的插入和多次更新。此次仅确认生成 SQL 错误，没有宣称已运行真实 PostgreSQL。建议责任：SQL 方言负责人。

### 码-07：快照行排序违反真实外键依赖（P1，已复现操作序列，静态核对 DDL）

- 位置：[sql_export.go](../../internal/engine/sql_export.go) 的 `repositoryRowsLocked` 结尾按表名字典序排序；[repository.go](../../internal/persistence/flowable/repository.go) 的 `DiffOperations/Apply` 按列表顺序执行；[MySQL DDL](../../internal/persistence/schema/sql/mysql/001-flowable-8.1.sql) 的 `ACT_FK_BYTEARR_DEPL`（第 770 行附近）。
- 触发：首次持久化一个带 BPMN 资源的部署。
- 实际：`ACT_GE_BYTEARRAY` 先于 `ACT_RE_DEPLOYMENT` 插入，资源的 `DEPLOYMENT_ID_` 所指父行尚不存在。临时测试按即时外键规则检查序列，直接失败。

### 码-10：变量类型往返不完整，未知类型可能静默变空（P1，已复现并静态确认）

- 位置：[sql_export_runtime.go](../../internal/engine/sql_export_runtime.go) 的 `variableRow/variableColumns`；[runtime_decode.go](../../internal/persistence/flowable/runtime_decode.go) 的 `RuntimeVariable`；[sql_import_runtime.go](../../internal/engine/sql_import_runtime.go) 的 `runtimeVariableValue`（第 257 行）。

- 实际：恢复值变为字符串 `"AQID"`，不再是 `[]byte`。二进制落入默认 JSON 编码分支，缺少 `BYTEARRAY_ID_` 关联读写。
- 静态确认：解码结构没有字节数组引用，未知变量类型会按现有文本/数字兜底，缺值时返回 `nil,nil`，可能把不可读的 Java 序列化变量误判为合法空值；大 JSON/长文本直接写 `TEXT_` 也没有体现真实列容量和外置字节存储策略。
- 修复与验收：制定类型兼容矩阵，支持类型完整往返；不支持类型在迁移预检和导入时返回明确阻断错误。覆盖 binary、长字符串、JSON、日期、数字精度、Java 序列化和历史变量数据读取。建议责任：变量与迁移负责人。

### 码-11：PostgreSQL 快照保存先删后插且没有事务（P0，静态确认）

- 位置：[sqlstate/store.go](../../internal/persistence/sqlstate/store.go) 的 `Save`（第 137 行）及 `DB` 接口。
- 触发条件：PostgreSQL 路径 DELETE 成功，随后 INSERT 因连接、取消或 SQL 错误失败；或进程在两条语句之间退出。
- 代码结果：旧快照已被删除，返回错误不能恢复数据库记录。`DB` 没有事务接口，两次执行在此路径没有同一事务保障。MySQL 工作区改成单条 upsert，仅修复 MySQL 路径。
- 修复与验收：PostgreSQL 改为单条原子 upsert 或显式事务；对故障阶段分别注入错误并从新连接读回旧快照。需真实 PostgreSQL 故障验证，本次未执行。建议责任：状态存储负责人。

### 码-12：当前架构仍是全内存、全状态快照，缺乏集群协调（P1，已知限制）

- 位置：[engine.go](../../internal/engine/engine.go) 的全局 `mu` 和 `execute`；[job.go](../../internal/engine/job.go) 的 `dueJobIDs/runOneJob`；[sqlstate/store.go](../../internal/persistence/sqlstate/store.go) 的固定 `flowable-go-state` 记录。
- 现状：每条写命令在引擎级互斥锁下复制全部状态；快照模式序列化全部状态；行模式仍导出全量再比较。读接口主要遍历内存，未变成数据库分页查询。作业从本地内存取出，没有跨节点抢占和执行前数据库仲裁。
- 影响：单次操作成本随历史总量增长。MySQL 单条 upsert 可避免单次写入撕裂，但不能阻止两个进程用旧快照互相覆盖；两个节点也可能执行同一业务委托。即使修好 REV_，提交时冲突仍不能撤销已经发生的外部副作用。
- 修复与验收：首阶段明确单进程独占并在部署/启动层实施约束；后续改成命令级事务与受影响实体工作单元、真实查询分页、数据库作业抢占、租约与幂等机制。双节点竞争、锁过期、节点退出和大量历史数据均需测试。建议责任：架构、作业、性能负责人。

// TestPostgresUpdatePlaceholder 验证更新参数按实际追加顺序编号。
// @param t 测试上下文
// @return 无
func TestPostgresUpdatePlaceholder(t *testing.T) {
    row, err := NewRow("ACT_RE_MODEL")
    if err != nil {
        t.Fatal(err)
    }
    if err := row.SetInsertColumns([]string{"ID_", "REV_", "NAME_"}); err != nil {

    for column, value := range map[string]any{"ID_": "m1", "REV_": 1, "NAME_": "修改"} {
        if err := row.Set(column, value); err != nil {
            t.Fatal(err)
        }
    }
    query, _, err := row.UpdateSQL("postgres", 1)
    if err != nil {
        t.Fatal(err)
    }
    want := "UPDATE ACT_RE_MODEL SET REV_ = $1, NAME_ = $2 WHERE ID_ = $3 AND REV_ = $4"

        t.Fatalf("更新 SQL 参数位置错误：%s", query)
