# 006 系列文档之五：阶段 0（P0.1 + P0.2）DDL 与行仓储实现记录

> 记录 P0.1（workflow_\* 表 DDL 双库）与 P0.2（行仓储层）的实现决策与验收结果。行为规格见 003-表结构.md，存储设计见 002-架构与映射.md §5。

## 1. 关键决策

### 1.1 表数量：22 张（21 保留 + workflow_business_system）

003 文档标题与开发计划写"24 张保留"，但两份文档的**逐表明细清单均为 21 张保留表**：

- 003 §1 枚举 21 保留 + 1 新增；
- 开发计划 §3.3"保留并建表"枚举同样 21 张，并明确裁剪旧委托两表（workflow_delegate/workflow_consigner）与旧遗留四表；001 文档另裁剪 workflow_rule；workflow_role 未进入任何保留清单。

多出的 3 张表只能来自上述已被明确裁剪的表，故按明细清单实现 **22 张**。后续如需补表：新增 DDL 段落 + `tables.go` 表定义 + 仓储文件即可（EnsureSchema 对部分表的检测会拒绝在残缺结构上启动，属预期保护）。

### 1.2 schema 包多文件与 checksum 语义

- `Load/Tables/Checksum/TableColumns` 语义收敛到**引擎 001 脚本**，`schema.Checksum("mysql"/"postgres")` 的值**保持不变**（基准值以 `TestChecksumStable` 固化在 schema 包测试中），既有库升级校验不受影响；
- 新增 `Files(dialect)`（按文件名序枚举 001→002）、`LoadFile(dialect, file)`、`ChecksumFile(dialect, file)`（workflow DDL 独立校验和）、`FileTables(dialect, file)`；
- `EnsureSchema`（mysql/postgres）拆为两段：`ensureEngineSchema`（原逻辑不变）→ `ensureWorkflowSchema`（002 独立计数、独立 checksum 标记 `flowtide.workflow.schema.checksum` 写入 ACT_GE_PROPERTY）。引擎表已初始化的库只补跑 002；任一段部分表/标记不匹配都会拒绝启动；
- `TableColumns` 表体解析改为在 `)`（可带 ENGINE 表选项）后遇 `;` 截止，不再吞并表外索引/插入语句，且支持转义列（`` `condition` `` / `"condition"`）。

### 1.3 行仓储（internal/persistence/workflow）

- 方言感知：mysql `?` / postgres `$n`；`condition` 列按方言转义（反引号/双引号）；条件更新用相对占位符整体平移（`shiftPlaceholders`）；
- `Row = map[string]any` 通用行载体，列名严格按 `tables.go` 表定义校验后拼 SQL（防注入）；INSERT 参数按表定义列序输出，保证确定性；
- 工作单元 `WithTx(ctx, fn)`：事务经 ctx 传递（`executorFrom` 解析 *sql.Tx / *sql.DB），嵌套调用复用外层事务；错误或 panic 回滚；
- 公共列自动填充：create_time/update_time 由仓储层填充，时间源可注入（`WithClock`）；**ID 由调用方传入**（internal/idgen），缺失即报错；creator/updater 由上层显式传入（铁律 4）；
- 22 张表全部有仓储（每表一文件），通用方法集：Insert / UpdateByPK / DeleteByPK / GetByPK + 常用查询（NextActivity 的 used=0 查询与 MarkUsed 回写、InsertDual 双写；MessageExtend 按 task/processInstance/business/owner 查删；Document 按 business_id+tenant upsert 与逻辑删除；HisStep 按 deploymentId；ReviewTask 待审/已审；TaskException handle_status 流转；TaskDelegate 启用规则/退休；Consigners/ConsignObj、Remind/RemindTarget、BusinessSystem 等见各文件注释）。

## 3. 验收结果（2026-10-31）

- `go build ./...`、`go vet ./internal/persistence/...` 全绿；`go test ./internal/persistence/... ./internal/workflow/...` 全绿（adminpage 包的 Content-Type 断言失败为 Windows mime 注册表环境问题，与本任务无关、改动前即失败）；
- 单测行覆盖率：workflow 包 97.7%（≥0.9 达标）；
- 真实 MySQL 8.0.35（172.16.3.5:4407）：`FLOWABLE_MYSQL_INTEGRATION=1` 下 TestIntegrationMySQLSchema（引擎+workflow 两段 EnsureSchema、重复幂等）与 TestIntegrationWorkflowMySQL（22 表往返 + 预生成-消耗闭环 + upsert + 异常流转 + WithTx 提交/回滚）通过；
- 真实 PostgreSQL（172.16.3.2:5432）：`FLOWABLE_POSTGRES_INTEGRATION=1` 下 TestIntegrationPostgresEnsureSchema 与 TestIntegrationWorkflowPostgres 通过。

## 4. 遗留与风险

1. `.env` 中 `db_pg_schame=flowable-go-dev` 含连字符，`pgstore.LoadDSN` 会拒绝（"必须是单个合法标识符"）；PG 集成验证需显式提供 `FLOWABLE_POSTGRES_DSN`（实测用 `search_path=public`），后续如需按租户 Schema 建表应调整该配置或校验规则；
2. 007 调研中的前端界面扩展字段（markProcessCompleted、parallelBranchReturn 等 30+ 项）未纳入 P0.1 DDL——本轮规格以 003 §1 列名为准，待 P5/P6 实现对应能力时再补列；
3. workflow_marker 与引擎标记同存 ACT_GE_PROPERTY：若外部工具只建了 workflow 表未写标记，EnsureSchema 会拒绝接管（预期严格行为，需人工迁移）；
4. `flowtide-migrate` 的 `-list-tables`/SQL 导出目前仍只输出引擎 001，002 导出未接入（EnsureSchema 已覆盖实际迁移路径）。
