## 2. 监听器控制机制（listener_ext.go 设计）

引擎原有 `ExecutionListener func(ctx, *Execution) error` 已经能在命令内改变量（`Execution.SetVariable`），
但 `*Execution` 是 internal/engine 内部类型，workflow 包（仅依赖 api.Engine）无法触达，且拿不到
`commandContext`（无法登记 Defer）。对位 `api.HookControl` 模式新增：

1. `api/listener.go` 定义 `ListenerControl`（SetVariable/SetVariableLocal/Defer）与
   `ExecutionListenerHook func(ctx, ListenerExecution, ctl) error`；
2. `internal/engine/listener_ext.go` 实现：注册表 `executionListenerHooks`（Engine 新字段）+
   调用点适配 `invokeExecutionListenerHooks`（构造快照与控制句柄）；
3. `execution_listeners.go#invokeExecutionListeners` 最小接线：class/delegateExpression 名解析后
   先查扩展监听器，命中即执行（错误 → `ENGINE-1943` 回滚），未命中回退原生 `executionListeners` 表；
4. workflow 侧经 `api.ExecutionListenerRegistrar` 接口断言注册（`RegisterCountersignListeners`）。

**接线约定（重要）**：监听器在引擎命令内同步执行，命令持有引擎互斥写锁，监听器内调用
`GetBpmnModel` 等引擎公有 API 会重入死锁（与 executor_rewrite.go 同一约束）。因此会签监听器
只读 Warmup 预热缓存——**部署新定义后必须调用 `CountersignService.Warmup/WarmupAll`**
（未预热时报 `WORKFLOW-2104 会签节点元数据未预热`，命令失败）。

## 3. 执行者来源优先级（与调研文档表述的差异）

按 Java 源码实现（调研文档 004 §5 的"优先级"表述与代码相反）：

1. 模型 `executorType`+`executorList`（person 直用 identityId；org/role 经组成员查询展开，
   未注入查询或展开失败时保留组 ID 原值——Java 即原样透传）；
2. `next_activity` 已有预存记录覆盖（person→identityId，否则 groupId；来源服务可选注入，nil 跳过）；
3. 业务变量 `customExecutorList` 最终覆盖（`randomSort=true` 先 shuffle）。

最终去重（保持首次出现顺序），空集合抛 `会签集合不能为空`。写 `executorList`（覆盖）、
`nrOfInstances=len`（覆盖）、`countersignPass/countersignReturn`（**仅缺失时置 0**——引擎对
串行会签逐实例重放 start 监听器，无条件覆盖会把已累计的计数清零，此为有记录的 Java 偏差修复）。

## 4. 权重会签

- `countersignByWeight` 监听器：先同集合配置，再校验 `weightThreshold` 非空（缺省抛
  `未设置会签权重阈值`），写 `totalWeight=0`/`weightThreshold`（模型原值，可为表达式串）/
  `countersignByWeight=true`；
- 办结侧 `totalWeight` 累计已由 complete.go `accumulateCountersignWeight` 实现，本阶段不重复；
- 通过/否决判定交给 BPMN 完成条件表达式（`multiInstance` Bean 语义）：语料
  `${totalWeight >= weightThreshold || totalWeight <= -weightThreshold || nrOfCompletedInstances == nrOfInstances}`
  覆盖"累计达标通过 / 负累计绝对值达标否决（一票否决 = rejectWeight 巨大）/ 全部完成未达标否决"；
- 权重数据：`CountersignWeightStore` 端口（`workflow_countersign_weight` 表，definitionKey+activityId
  唯一维度，先删后插），内存实现 `MemCountersignWeightStore` + SQL 适配 `SQLCountersignWeightStore`
  （组合 pwf 仓储，逐主键删除等价无条件删除）；`ListNodeWeights` 存储优先、模型 weightList 回退。

## 5. 比例退回基础（decimal 精度方案）

`CountersignPercentResult(ctx, taskID, countersignResult)`（供 complete 链调用）：

1. `StepRuleProvider` 端口读取 his_step 规则（P3-A 接口位，nil 或未启用 → 恒"不超线"）；
2. 结论合法性（0 否决 / 1 通过）→ 累计 `countersignReturn`/`countersignPass`（实例级变量写回）；
3. 全部实例完成（pass+return == nrOfInstances）才判定；`returnPercent` 缺失抛 `未设置会签退回比例`；
   无退回票不判定；
4. 比较 `countersignReturn/(pass+return) >= returnPercent/100`：shopspring/decimal v1.4.0 定点比较
   （go.mod 已加依赖），修复 Java `NumberFormat` 两位小数格式化的四舍五入误判；阈值恰好相等
   （0.5 == 50%）按 Java `compare >= 0` 语义判超线（有测试锚定）。

## 6. 加签/减签

- `AddSign`（对位 addSignTask:311 + createSignSubTasks:352）：首层加签将当前任务改造为父任务
  （owner=操作人、assignee 置空、任务局部变量 `countEnabled=true`/`scopeType`），为每个被加签人
  建子任务（挂顶层父任务），并为加签人建占位子任务立即办结；二层加签新子任务与既有子任务平级、
  当前子任务立即办结；候选人清理（加签人是父任务候选时移除）→ QJQ/HJQ 意见 → 操作记录 →
  新子任务待办 + 已办镜像、父任务待办标记 consigner。
- **引擎侧适配（有意偏差）**：Go 引擎 `Resolve` 校验 `DelegationState==PENDING`（Java Flowable
  resolveTask 无此校验），而办结联动 `handleParentTaskAfterComplete` 以 Resolve 归还父任务——
  故 AddSign 在改造父任务后追加 `Delegate(parent, operator)` 保持 PENDING 委派态，否则
  加签办结联动必然失败。
- `DelSign`（Java 无任务级减签对位源码，按加签逆操作定义）：删子任务（保留历史）+ 意见
  （类型与作用域对应：before→QJQ/after→HJQ）+ 删子任务待办/已办；剩余子任务为空时 Resolve
  恢复父任务（assignee=owner），after 作用域下父任务随之办结。
- 完成联动（子任务全完成 → 父任务 resolve/办结）由 complete.go `handleParentTaskAfterComplete`
  实现，加签侧仅保证父任务状态与其兼容（PENDING）。

## 7. 多实例动态加减成员（引擎能力结论）

Java 用 `runtimeService.addMultiInstanceExecution(nodeId, proInstId, {assignee})` /
`deleteMultiInstanceExecution(executionId, completed)`。**Go 引擎 RuntimeService 无等价 API**
（无动态创建/销毁多实例子执行的实现），P3-A 不在引擎侧补齐。已留接口位
`MultiInstanceMemberPort`（AddMember/RemoveMember，可注入承接未来引擎能力）；
workflow 侧实现 `AddMultiInstanceMember`/`RemoveMultiInstanceMember`：executorList 追加/移除
（去重幂等）+ `nrOfInstances` 同步。

## 8. 部署强校验（P3.6）

- `CountersignService.ValidateCountersignConfig(ctx, definitionID)`（对位 checkCountersignListenerConfig:316）：
  凡 `MultiInstance!=nil` 节点——weightType=average 需含 `countersignCollectionConfig`（或 Java
  全限定类名后缀 `CountersignCollectionConfigExecutionListener`，线上语料兼容）；=custom 需含
  `countersignByWeight`（同理）且 `weightThreshold` 非空（缺省报 `未设置会签权重阈值`）；
  weightType 缺失按 Java 语义（命中标记不置位）报未配置监听器。
- `ValidateProcessIDMatch(process, expectedKey)`：id 空 → `流程定义key为空`；不一致 →
  `导入流程与当前流程不匹配，请检查后重试。`。
