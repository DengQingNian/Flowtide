## 2. 核心发现：同一个"装配断链"模式

审计中发现多处能力具备以下共同特征：**代码完整、单测通过、但生产装配层从未接线**。
单测无法发现此类缺陷，因为测试会自行构造完整依赖。

| 能力 | 现状（审计时） | 影响 |
| --- | --- | --- |
| 会签比例退回规则端口 | WithCountersignRules 生产零调用 | 比例退回恒为未启用 |
| 会签 next_activity 来源 | WithCountersignNext 生产零调用 | 预存执行者覆盖失效 |
| 会签执行监听器 | RegisterCountersignListeners 零调用 | 集合配置/权重监听器永不触发 |
| 业务回调 client | SendTaskCallback 只在测试中调用 | D5 回调能力完全不生效 |
| 回调异常记录器 | WithCallbackRecorder 未装配 | 回调失败不落异常表 |
| 业务系统注册存储 | 未进入能力存储集合 | 回调地址无处可查 |
| SQL 模式待办源 | emptyTodoSource 占位 | 三大调度空转 |

本文新增 `TestAssembly_*` 系列守卫用例（wiring_reachability_test.go），
以装配结果为准做静态断言，防止此类缺陷回归。

## 4. 本次整改的实现要点

### 4.1 会签子系统（A2/A3/A4/A5/A6）

- facade_ops.go：会签选项从"仅权重"扩为"权重 + next_activity 来源 + 比例退回规则"；
  成员查询按 Java ProcessesUtil.getExecutorMap 语义**故意不注入**（集合配置阶段保留组 ID，展开发生在推演器）。
- complete.go：parseWeightConfigs 兼容 "id"（Java 权威）与 "identityId"（Go 历史），两键并存以 id 为准。
- api/workflow.go：CompleteTaskVo 增加 CountersignResultSet 与 UnmarshalJSON，
  使"未传"与"显式 0（否决）"可区分；服务层未显式设置时报 WORKFLOW-2010。
- countersign.go：新增 isStepRuleLookupError，规则定位失败（任务/定义不存在）按未启用处理，
  存储故障仍向上抛出 —— 避免"普通实例调用 complete/sign 退化为失败"。

### 4.2 业务回调（A7/A8/A9）

- 新增 internal/workflow/business_callback_hook.go：
  钩子在 TASK_CREATED 内**只组包**，HTTP 发送经 ctl.Defer 延迟到命令提交并释放锁后执行
  （钩子持有引擎写锁，锁内发 HTTP 会阻塞全部命令）。
- BusinessCallbackHook 读预热缓存的节点元数据；未预热时降级为延迟预热，本次不发送。
- 回调失败经 CallbackClient 的 ExceptionRecorder 落 workflow_task_exception（D5）。
- 节点通过 BPMN 扩展属性 businessCallback（"true"）与 businessCallbackParams 声明是否回调。

### 4.3 装配可达性守卫（A11 及通用防护）

新增 wiring_reachability_test.go，断言：
- 会签规则端口与 next 来源已注入、成员查询未注入；
- 业务回调 client 与钩子已装配、异常记录器不是 Nop；
- 部署后预热入口可安全调用。

### 4.6 集成测试基础设施修复

打通真实库测试时发现三处测试基础设施缺陷（非产品缺陷）：

1. **PostgreSQL Schema 引导顺序错误**：连接 DSN 携带 `search_path`，而 Schema 不存在时建连即失败，
   代码却先 `Open` 后 `CREATE SCHEMA`。已改为先以无 search_path 的连接建 Schema 再建业务连接
   （integration_test.go、store_sql_integration_test.go 两处）。
2. **business_integration_test.go 回调断言与注释不符**：注释称"空地址静默跳过、真实网络零请求"，
   却注册了不可达地址 http://oa/task 并真实发起回调（DNS 失败重试 4 次）。已改为断言未注册租户的跳过语义。
3. **PostgreSQL 测试只认环境变量**：persistence/postgres 与 migration 包的集成测试直接读
   `FLOWABLE_POSTGRES_DSN`，未设置时 t.Fatal，与 workflow 包"环境变量优先、退回 .env"不一致，
   导致设置了 `FLOWABLE_POSTGRES_INTEGRATION=1` 仍全部失败。已统一为环境变量优先、退回仓库根 `.env`。
4. **隔离库 Schema 未预建**：DSN 携带 search_path 指向的 Schema 在新建库中不存在时建连即失败。
   已在 persistence/postgres、persistence/workflow、migration 三处补"先用无 search_path 的连接建 Schema"引导。
5. **Schema 名二次加引号**：含连字符的 Schema 名经 LoadDSN 已加双引号，测试再用 `strconv.Quote` 包裹会
   产生 `""name""` 导致 `syntax error at or near`。已改为检测首字符后再决定是否加引号。

> 说明：`.env` 的 `db_pg_schame=flowable-go-dev` 保持原值未改——根因是产品代码
> `config.go` 的 Schema 正则只允许合法标识符，拒绝了 PostgreSQL 实际支持的带连字符 Schema 名。
> 已修复该正则并对特殊字符 Schema 名加双引号，属真实代码缺陷修复而非配置妥协。仅在 `.env` 补 `db_pg_sslmode=disable`（`.env.example` 已注明本地无 TLS 库需显式设置）。

### 4.7 预存-消耗补偿（B3 部分）

审计指出的 P0 问题中，"预存成功后引擎命令失败导致 used=0 记录残留"是错派执行人的直接来源。
本轮在办结路径完成补偿（complete.go）：

- 预存成功后登记 `defer` 补偿；
- 函数以错误返回时，按"实例 + 目标节点"清理本次预存记录；
- 收尾链成功即置 `committed = true`，成功路径不执行补偿（保留预存给新任务消费）；
- 补偿本身失败只记日志，不改变返回值。

配套用例 complete_presave_test.go：成功路径断言"保留 1 条预存 + 历史双写不丢"，
失败路径断言"重复办结后记录数回到补偿前"。

> 剩余：钩子在引擎写锁内直接 UPDATE 账本（executor_rewrite.go）仍无回滚语义，
> 需引擎提供命令级事务钩子才能根治，属后续阶段（§6 第 1 项）。

   并在 CI 补跑 -race（Linux + CGO）。
