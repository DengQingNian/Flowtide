# 062 任务查询下推

> 文档编号：002-062
> 更新日期：2026-10-28
> 对应任务：MySQL 行仓储模式下 ACT_RU_TASK 查询下推

## 1. 背景与目标

行仓储模式此前虽然把运行状态写入 Flowable 兼容的 ACT_* 表，但 `Engine.ListTasks` 仍遍历内存中的 `e.state.Tasks` 完成过滤、排序和分页。任务量增大后，每次查询都要扫描全部运行任务并复制 DTO，数据库中的索引无法参与。

本次为运行任务增加 SQL 下推：

- 新增 `flowable.TaskQuery` 与 `(*Repository).QueryTaskIDs`，在 ACT_RU_TASK 上执行 COUNT 与分页 ID 查询；
- `Engine.ListTasks` 在安全条件下使用 SQL 返回的任务 ID，再从内存映射任务、执行租户校验并转换为 DTO；
- 总数直接采用 SQL COUNT 结果；
- 不满足下推条件、或 SQL 失败时，不改变原有内存路径的语义；SQL 失败直接返回错误，不静默回退。

## 2. 下推触发条件

只有同时满足以下条件才会走 SQL 下推（`Engine.canPushdownTaskQuery`）：

1. 引擎配置了 `RowRepository`；
2. 请求的 `TaskFilter.TenantID` 为空；
3. 请求上下文租户与引擎默认租户均为空（`e.tenantOf(tenant.From(ctx)) == ""`）；
4. 内存状态中不存在任何非默认租户数据（`hasNonDefaultTenantData` 为假）。

第 3 条中"上下文中绑定空租户"等同于默认租户，REST 邻居中间件总会绑定租户上下文，因此不能用"是否绑定"判断，而应使用生效租户值。租户非空时保留内存路径。

第 4 条用于避免多租户数据被 SQL 无租户条件误计入：行模式通过 `LoadAll` 恢复时可能加载多个租户的任务。此时 SQL 的 COUNT 与分页会把其他租户任务算进来；即使 `allowTask` 能过滤返回的 DTO，`total` 仍会偏大、分页也会被挤占。因此只要内存中存在非空租户的任务或实例，本次查询整体回退内存路径。

## 3. 下推字段与 SQL 形状

### 3.1 直接列过滤

| TaskQuery 字段 | SQL 条件 |
| --- | --- |
| `Assignee` | `T.ASSIGNEE_ = ?` |
| `Owner` | `T.OWNER_ = ?` |
| `DelegationState` | `T.DELEGATION_ = ?` |
| `ProcessInstanceID` | `T.PROC_INST_ID_ = ?` |
| `ParentTaskID` | `T.PARENT_TASK_ID_ = ?` |

均为参数化比较，值不参与 SQL 文本拼接。

### 3.2 流程定义 Key

`ProcessDefinitionKey` 使用内连接，谓词位于 ON 中：

```sql
ACT_RU_TASK T
INNER JOIN ACT_RE_PROCDEF P
  ON P.ID_ = T.PROC_DEF_ID_ AND P.KEY_ = ?
```

JOIN 谓词在 SQL 文本中先于 WHERE 出现，构造时先追加该参数，保证 PostgreSQL 的 `$n` 编号与文本顺序一致。

### 3.3 候选人

`CandidateUser` 追加两个条件：

```sql
(T.ASSIGNEE_ IS NULL OR T.ASSIGNEE_ = '')
AND EXISTS (
  SELECT 1 FROM ACT_RU_IDENTITYLINK L
  WHERE L.TASK_ID_ = T.ID_
    AND L.TYPE_ = 'candidate'
    AND (L.USER_ID_ = ? OR L.GROUP_ID_ IN (?, ?))
)
```

- 任务已签收（ASSIGNEE_ 非空）时被排除；
- 候选组来自 `Engine.candidateGroupsForUser`，由 `e.state.Memberships` 中 `用户|组` 键推导，按字典序排序，与内存 `matchesTask` 的成员关系语义一致；
- 候选组为空或全部为空字符串时只保留 `L.USER_ID_ = ?`，不会生成非法的 `IN ()`；
- 用户候选与组候选都要求 `TYPE_ = 'candidate'`。

### 3.4 排序与分页

```sql
SELECT COUNT(*) FROM <FROM> <WHERE>;

SELECT T.ID_ FROM <FROM> <WHERE>
ORDER BY T.CREATE_TIME_ ASC, T.ID_ ASC
LIMIT <n> OFFSET <m>;
```

- 排序固定为创建时间升序、ID 升序，与内存路径的排序键一致；
- 分页参数规范化与 `Engine.normalizePage` 一致：`start < 0` 归零，`size <= 0` 取 10，`size > 1000` 封顶 1000；
- MySQL 使用 `?`，PostgreSQL 使用 `$1...$n`，复用仓储既有的 `placeholder` 规则；
- COUNT 与 ID 查询分两次执行，均使用同一套 FROM/WHERE 与参数前缀。

### 3.5 错误处理

| 场景 | 错误码 |
| --- | --- |
| 请求携带租户过滤 | `ROW-0035` |
| 数据库不支持查询 | `ROW-0017` |
| COUNT 查询、扫描或遍历失败 | `ROW-0036` |
| ID 查询失败 | `ROW-0037` |
| ID 扫描失败 | `ROW-0038` |
| ID 遍历失败 | `ROW-0039` |

错误统一为中文 `api.Error`，消息不拼接 SQL 文本或参数值；底层错误仅作为 `Cause` 保留。

## 4. 未下推字段与边界

以下内容本次**没有**下推，仍在内存路径或尚未支持：

- **租户过滤**：`TaskFilter.TenantID` 非空时完全走内存；多租户数据存在时也不下推（见第 2 节）。
- **变量过滤**：`TaskFilter` 本身没有变量条件；任务变量仍在 `toTaskDTO` 中从内存装配。
- **候选组扩展查询**：没有独立的 `candidateGroups` 过滤字段；组候选只能通过 `CandidateUser` + 成员关系间接命中。
- **其他列**：任务名称、描述、优先级、到期时间、创建时间区间、流程定义 ID 等当前不在 `TaskFilter` 中，未提供 SQL 条件。
- **排序与分页参数**：REST 的 `sort`/`order` 未映射到 `TaskFilter`，SQL 排序固定，不支持自定义排序。
- **总数与可见性**：下推路径的 `total` 来自 SQL。若内存与数据库短暂不一致（如任务已被删除但 ID 仍返回），`allowTask` 或 `mapTaskIDs` 会跳过该 ID，此时 `total` 可能大于实际 `Data` 长度。正常行模式下每条命令成功后才返回，二者应一致。

## 5. 与内存路径的一致性

- 过滤语义：直接列、流程定义 Key、候选人/候选组均与 `matchesTask` 对齐；任务分配后 `ASSIGNEE_` 为空条件会排除，与内存 `Assignee != ""` 判断一致。
- 排序：SQL 与内存都使用 `CREATE_TIME_ ASC, ID_ ASC`。MySQL `CREATE_TIME_` 为 `timestamp(3)`，同一毫秒内创建的任务由 ID 决定顺序，与内存排序键一致。
- 分页：`Start/Size` 规范化规则相同，返回 `Page.Start/Size` 一致。
- 可见性：下推结果仍逐个执行 `allowTask`，不会绕过租户校验返回不可见任务。
- 失败策略：SQL 查询失败直接返回错误，不静默回退内存，避免掩盖数据库或 Schema 问题。
- 回退策略：租户过滤、非空生效租户、多租户内存数据都会走原有内存路径，行为与改造前完全一致。

## 6. 性能边界

- 每次下推固定两次数据库往返（COUNT + 分页 SELECT），比内存过滤多网络开销，但避免全量任务扫描与 DTO 复制。
- COUNT 使用与列表相同的 JOIN/EXISTS 条件；候选人查询依赖 `ACT_RU_IDENTITYLINK(TASK_ID_)` 上的索引，大候选组会产生多个 `IN` 参数。
- 列表查询按 `ORDER BY T.CREATE_TIME_ ASC, T.ID_ ASC` 排序，Schema 仅有 `ACT_IDX_TASK_CREATE(CREATE_TIME_)`；复合排序和大偏移量 `OFFSET` 在深分页时仍可能扫描较多行。
- 下推查询在 `Engine.read` 的读锁内执行，数据库往返期间会阻塞写命令；慢查询会直接拉长写延迟。
- `hasNonDefaultTenantData` 每次查询遍历内存任务和实例判断是否存在非默认租户，复杂度 O(任务数 + 实例数)，只做字段判断，不复制 DTO；在单租户库中为固定额外开销。
- 候选组来自内存成员关系映射，未额外查询 ACT_ID_MEMBERSHIP；行模式重启后成员关系是否完整取决于现有行导入范围，与改造前一致。
- 单条 SQL 的 `LIMIT` 已封顶 1000，避免一次拉取过多 ID；但 COUNT 是精确统计，大表上仍可能有成本。

## 9. 剩余风险

1. 多租户数据存在时整体回退，任务量大时仍需内存扫描；后续应在 SQL 中增加租户列过滤并重新评估 `total`。
2. MySQL 8.0.35 已通过真实临时库集成验证；PostgreSQL 仍未验证，实际索引选择、执行计划和深分页成本未知。
3. 候选人 SQL 依赖 ACT_RU_IDENTITYLINK 的 `TASK_ID_`、`TYPE_`、`USER_ID_`、`GROUP_ID_`；Schema 若缺少相关索引，大表下 EXISTS 可能退化。
4. 候选组仅在内存成员关系完整时正确；行模式对 ACT_ID_MEMBERSHIP 的持久化范围未在本次覆盖。
5. `CREATE_TIME_` 为毫秒精度，跨命令同毫秒创建的任务依赖 ID 排序；极端情况下与内存完整纳秒时间排序可能不同。
6. 下推失败策略为直接报错，数据库短暂不可用会让任务列表查询失败，不会降级；这是有意的可观测性取舍。
