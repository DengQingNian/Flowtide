# 057 双向 TLS 认证

> 文档编号：002-057
> 更新日期：2026-10-28
> 对应计划：011 REST API 与兼容契约

## 1. 背景与目标

`cmd/flowtide-server` 此前通过 `-tls-cert` / `-tls-key` 调用 `http.Server.ListenAndServeTLS`，只实现单向 TLS：客户端校验服务端证书，服务端不校验客户端。本期在不修改 `internal/rest` 的前提下增加双向 TLS（mTLS）能力：

- 新增客户端 CA、客户端认证模式、TLS 最低版本三个参数；
- 由纯函数 `buildTLSConfig` 完成参数校验、CA 解析和 `tls.Config` 构造；
- 服务端证书仍由 `ListenAndServeTLS` 加载，配置文件路径不提前读取私钥；
- 客户端证书校验在 TLS 握手阶段生效，未通过握手的请求不会到达 REST Handler。

## 2. 命令行参数

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `-tls-cert` | 空 | 服务端证书路径（PEM）。为空表示不启用 TLS。 |
| `-tls-key` | 空 | 服务端私钥路径（PEM）。必须与 `-tls-cert` 同时配置。 |
| `-tls-client-ca` | 空 | 客户端 CA 证书文件路径（PEM），文件内可包含多个证书，用多个 `CERTIFICATE` 块拼接。设置后要求并校验客户端证书。 |
| `-tls-client-auth` | `none` | 客户端证书认证模式：`none`、`request`、`require-any`、`require-verify`；大小写不敏感，两侧空白会被忽略。 |
| `-tls-min-version` | `1.2` | TLS 最低版本：`1.2` 或 `1.3`，同时接受 `tls1.2` / `tls1.3` 写法。 |

认证模式语义：

| 取值 | `tls.ClientAuthType` | 行为 |
| --- | --- | --- |
| `none` | `NoClientCert` | 不请求客户端证书，保持原有单向 TLS。 |
| `request` | `RequestClientCert` | 向客户端请求证书，但不强制；不提供证书也能完成握手。 |
| `require-any` | `RequireAnyClientCert` | 要求客户端证书，但不校验证书链与用途，仅适合受控内网过渡。 |
| `require-verify` | `RequireAndVerifyClientCert` | 要求客户端证书，并校验证书链、有效期与客户端用途，推荐用于生产。 |

## 3. 参数校验规则

`buildTLSConfig(certFile, keyFile, clientCAFile, clientAuth, minVersion)` 在启动阶段完成全部校验，任一条不满足都会返回错误，`main` 打印"TLS 配置非法"后以退出码 1 结束：

1. `-tls-cert` 与 `-tls-key` 必须同时为空或同时非空；
2. 未启用 TLS（证书与私钥均为空）时，`-tls-client-ca` 必须为空，`-tls-client-auth` 必须为 `none`（含空值）；
3. 启用 TLS 但 `-tls-client-auth` 非 `none` 时必须配置 `-tls-client-ca`；
4. 配置了 `-tls-client-ca` 但未显式指定认证模式（仍为 `none`）时，按 `require-verify` 处理，避免"配置了 CA 却仍接受匿名客户端"的误配；
5. `-tls-client-auth` 取值必须属于上表四种；
6. `-tls-min-version` 取值必须为 1.2 或 1.3；
7. CA 文件必须可读，且至少包含一个可解析的 PEM 证书；
8. `-tls-min-version` 在未启用 TLS 时同样做取值校验，但不参与任何握手配置。

错误信息只包含参数名、文件路径和解析结果（如"没有有效的 PEM 证书"），不会输出证书或私钥内容；CA 文件读取失败时仅包装系统错误。

## 4. 启动示例

### 4.1 要求并校验客户端证书（推荐）

```bash
HOME=/root go run ./cmd/flowtide-server \
  -addr :8443 \
  -tls-cert server.crt \
  -tls-key server.key \
  -tls-client-ca client-ca.pem \
  -tls-client-auth require-verify \
  -tls-min-version 1.2
```

客户端访问：

```bash
curl --cacert ca.pem \
  --cert client.crt --key client.key \
  https://127.0.0.1:8443/healthz
```

若同时启用了 Basic Auth 或 JWT，还需要按原有方式携带 `Authorization` 头，二者互不替代（见第 6 节）。

### 4.2 仅单向 TLS（保持原有行为）

```bash
HOME=/root go run ./cmd/flowtide-server -addr :8443 -tls-cert server.crt -tls-key server.key
```

### 4.3 只设置 CA，隐式启用校验

```bash
HOME=/root go run ./cmd/flowtide-server -tls-cert server.crt -tls-key server.key -tls-client-ca client-ca.pem
```

等价于 `-tls-client-auth require-verify`。

### 4.4 典型误配与结果

| 配置 | 结果 |
| --- | --- |
| 只给 `-tls-cert` | 启动失败："TLS 证书与私钥必须同时配置" |
| 未给证书/私钥却给 `-tls-client-ca` | 启动失败："-tls-client-ca 需要同时配置 -tls-cert 与 -tls-key" |
| 未启用 TLS 却 `-tls-client-auth require-verify` | 启动失败，提示需要同时配置证书与私钥 |
| `require-verify` 但未给 `-tls-client-ca` | 启动失败："需要配置 -tls-client-ca" |
| `-tls-min-version 1.1` | 启动失败："非法的 -tls-min-version 取值" |
| CA 文件缺失、非 PEM 或只含私钥 | 启动失败，错误信息不含文件内容 |

## 5. 证书要求

- **格式**：服务端证书、私钥、客户端 CA 均为 PEM。CA 文件可拼接多个 `CERTIFICATE` 块；只要有一个块可解析即视为有效，无法解析的块会被忽略。
- **服务端证书**：由 `ListenAndServeTLS` 加载，证书的 SAN 必须包含客户端实际访问的域名或 IP（如 `127.0.0.1`、`localhost`），否则客户端校验失败。
- **客户端证书**：必须由 `-tls-client-ca` 中的某个 CA 签发，处于有效期内，且扩展密钥用途包含 `clientAuth`（或未限制用途）。`require-any` 模式不校验证书链，仅要求客户端提供证书。
- **私钥安全**：`buildTLSConfig` 不读取服务端私钥，私钥只在 `ListenAndServeTLS` 建立监听时加载；建议证书与私钥文件权限为 `0600`，私钥不要放入镜像或日志。
- **证书轮换**：当前只支持重启生效，未实现热加载。

## 6. 与 Basic / Bearer / JWT 的关系

mTLS 工作在传输层，HTTP 认证工作在应用层，两者相互独立、可叠加：

- 客户端证书不合法时 TLS 握手失败，请求不会进入 `internal/rest` 中间件，也不会产生业务日志或审计记录；
- mTLS 通过后，Basic Auth、静态 Bearer Token、JWT/JWKS 仍按原有配置执行，未携带合法凭据依然返回 401；
- mTLS 不注入用户身份、角色或租户上下文。RBAC 仍由 JWT 角色或 Basic/身份库用户决定，证书主体（CN/SAN）当前不参与授权；
- 只启用 mTLS、不启用任何 HTTP 认证时，通过握手的客户端等同于匿名可访问，与原有"未配置认证即放行"的语义一致；生产环境建议同时启用 JWT 或 Basic。

## 7. 实现说明

新增 `cmd/flowtide-server/tls.go`：

| 函数 | 职责 |
| --- | --- |
| `buildTLSConfig` | 校验参数、解析认证模式与最低版本、按需加载 CA，返回 `*tls.Config`；未启用 TLS 时返回 `nil`。 |
| `validateDisabledTLS` | 校验未启用 TLS 时客户端证书参数必须为默认值。 |
| `parseClientAuth` | 字符串到 `tls.ClientAuthType` 的映射。 |
| `parseTLSMinVersion` | 字符串到 `tls.VersionTLS12` / `tls.VersionTLS13` 的映射。 |
| `loadClientCAPool` | 读取 PEM 并构造 `x509.CertPool`，失败时不泄漏内容。 |

`cmd/flowtide-server/main.go`：

- 新增三个 flag，并在构造 `http.Server` 前调用 `buildTLSConfig`；
- 仅当返回的配置非空时设置 `server.TLSConfig = cfg`；
- 监听分支保持原样：有 `-tls-cert` 时调用 `ListenAndServeTLS(cert, key)`，否则调用 `ListenAndServe`。`ListenAndServeTLS` 会克隆 `TLSConfig` 并加载服务端证书，`ClientAuth` / `ClientCAs` / `MinVersion` 因此真正参与握手。

## 9. 限制与后续工作

1. **未实现证书吊销**：不支持 CRL、OCSP 或 OCSP Stapling，已签发证书在有效期内始终可用；轮换依赖重启。
2. **未做证书主体到身份/租户的映射**：CN、SAN、组织等信息不解析，不写入请求上下文，也不参与 RBAC 与租户隔离。
3. **`request` 模式不暴露证书**：未修改 `internal/rest`，业务层无法获取"客户端是否提供了证书"或证书内容，该模式目前仅改变握手行为。
4. **全局生效**：mTLS 对整个监听端口生效，无法按路径或按服务区分。
5. **`require-any` 不校验证书链**：只确认客户端持有某张证书，不具备身份保证，生产环境应使用 `require-verify`。
6. **未实现证书热加载与轮换**：证书、CA 更新需要重启进程。
7. **仅支持 TLS 1.2/1.3**：不支持 TLS 1.0/1.1，也未提供密码套件自定义参数。

后续如需按租户或用户做细粒度授权，可在 `internal/rest` 中通过 `r.TLS.PeerCertificates` 读取客户端证书并映射身份，本期未实现。
