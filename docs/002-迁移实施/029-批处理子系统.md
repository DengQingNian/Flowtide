# 029 批处理子系统

> 文档编号：002-029  
> 更新日期：2026-10-28  
> 对应计划：011 REST API 与兼容契约；013 里程碑、排期与资源计划

## 1. 背景

Flowable 将“按流程定义批量迁移实例”建模为批处理作业（Batch）与分片（BatchPart），
调用方可以通过管理端点查询批次进度、分片结果和失败原因。此前本仓库的
`batch-migrate` 只是同步循环迁移并返回 204，没有批次实体。

本期在不改变既有单实例迁移语义的前提下，补齐以下能力：

- 批次与分片的公共类型。
- 批次状态、快照持久化与深拷贝回滚。
- 同步执行的批次迁移方法。
- 批次、分片与统计的 REST 查询端点。
- `batch-migrate` 返回 201 与批次 JSON。

## 2. 公共类型

定义在 `api/types.go`：

### 2.1 Batch

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 批次 ID |
| type | string | 批次类型，本期固定为 process-instance-migration |
| total | int | 分片总数 |
| completed | int | 成功分片数 |
| status | string | in-progress / completed / failed |
| startTime | time.Time | 批次开始时间 |
| endTime | *time.Time | 批次结束时间，执行中为 null |
| tenantId | string | 目标流程定义租户 |

### 2.2 BatchPart

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | string | 分片 ID |
| batchId | string | 所属批次 ID |
| type | string | 分片类型，与批次一致 |
| processInstanceId | string | 待迁移流程实例 ID |
| status | string | queued / completed / failed |
| startTime | time.Time | 分片创建时间 |
| endTime | *time.Time | 分片处理结束时间 |
| errorMessage | string | 失败原因，仅失败分片有值 |

错误信息字段是本实现的扩展，Flowable 使用异常堆栈字段；本仓库先保存可读错误文本。

## 3. 引擎状态与快照

### 3.1 运行时状态

`internal/engine/state.go` 新增：

~~~go
type batchState struct {
    Info  api.Batch
    Parts map[string]*api.BatchPart
}
~~~

`state` 新增 `Batches map[string]*batchState`，`newState` 初始化空映射。
`cloneState` 对批次信息、分片和结束时间做深拷贝，保证命令失败回滚不会污染原状态。

### 3.2 JSON 快照

`internal/engine/snapshot.go` 新增快照字段 `batches`：

~~~json
{
  "batches": [
    {
      "info": {"id": "...", "type": "process-instance-migration", "total": 2},
      "parts": [
        {"id": "...", "batchId": "...", "processInstanceId": "pi-1", "status": "completed"}
      ]
    }
  ]
}
~~~

- 保存时按分片 ID 排序，保证同一状态多次落盘结果稳定。
- 恢复时重建 `Batches` 映射，并保留分片结束时间与错误信息。
- 快照未包含的历史状态文件兼容：`batches` 缺省时批次为空。

### 3.3 与 SQL 行映射的关系

本期**不做** ACT_RU_BATCH / ACT_RU_BATCH_PART 的行映射：

- `toSnapshot` / `loadState` 只覆盖 StateStore / StatePath 的 JSON 快照。
- 当引擎以 RowRepository 为唯一状态源（`rowSource=true`）时，`saveState` 直接返回，
  批次不会写入关系表，重启后不可恢复。
- 因此批次功能默认要求启用文件状态存储；纯行仓储模式只保证进程内可见。

后续如补齐行映射，需要新增批次表 Schema、导出/导入逻辑并同步 `sql_export*` 系列文件。

## 4. 引擎方法

以下方法加入 `api.ManagementService`，由 `*engine.Engine` 实现。

### 4.1 ListBatches

```go
ListBatches(ctx context.Context) ([]Batch, error)
```

返回全部批次。按 `startTime` 倒序、`ID` 升序稳定排序，相同开始时间下结果确定。

### 4.2 GetBatch

```go
GetBatch(ctx context.Context, batchID string) (Batch, error)
```

批次不存在返回 404（`ENGINE-0700`）。

### 4.3 ListBatchParts

```go
ListBatchParts(ctx context.Context, batchID string) ([]BatchPart, error)
```

批次不存在返回 404；分片按开始时间升序、ID 升序稳定排序。

### 4.4 GetBatchPart

```go
GetBatchPart(ctx context.Context, partID string) (BatchPart, error)
```

在全部批次中查找分片，不存在返回 404（`ENGINE-0701`）。

### 4.5 BatchMigrateProcessInstances

```go
BatchMigrateProcessInstances(ctx context.Context,
    targetDefinitionID string,
    instanceIDs []string,
    activityMappings map[string]string) (Batch, error)
```

执行流程：

1. 空实例列表返回 400（`ENGINE-0702`）。
2. 只读校验目标流程定义存在且租户可见，不存在返回 404（`ENGINE-0404`）。
3. 在一个命令事务内创建批次和全部分片：
   - 批次：`type=process-instance-migration`、`total=len(instanceIDs)`、
     `status=in-progress`、`startTime=now`、`tenantId=目标定义租户`。
   - 分片：`status=queued`、`processInstanceId=实例 ID`、`startTime=now`。
4. 同步逐个调用 `MigrateProcessInstance`：
   - 成功：分片 `status=completed`。
   - 失败：分片 `status=failed`，错误文本写入 `errorMessage`，继续处理其余实例。
   - 每个分片处理完成后写入 `endTime`。
5. 汇总：
   - `completed` 为成功分片数。
   - 全部成功时批次 `status=completed`，否则 `status=failed`。
   - 写入批次 `endTime`。
6. 返回最终批次。

说明：迁移调用本身是独立事务；某一实例失败不会回滚已成功的实例，但不会影响批次与分片的记录。
批次创建、分片更新、批次汇总分别使用独立命令，避免在命令锁内递归调用迁移。

## 5. REST 端点

以下处理器位于 `internal/rest/batches_extra.go`，**本期不修改 server.go 注册路由**，
建议由主代理按下列模式接入：

```go
s.mux.HandleFunc("GET /service/management/batches", s.handleListBatches)
s.mux.HandleFunc("GET /service/management/batches/{id}", s.handleGetBatch)
s.mux.HandleFunc("GET /service/management/batches/{id}/batch-parts", s.handleListBatchParts)
s.mux.HandleFunc("GET /service/management/batches/{id}/summary", s.handleBatchSummary)
s.mux.HandleFunc("GET /service/management/batch-parts/{id}", s.handleGetBatchPart)
```

### 5.1 批次列表

`GET /service/management/batches`

查询参数：

- `type`：批次类型精确匹配。
- `status`：批次状态精确匹配。
- `tenantId`：租户精确匹配；未提供时读取 `X-Tenant-Id` 请求头。
- `page` / `size`：页码从 0 开始，`size` 默认 10、上限 1000。
- `start`：兼容既有分页写法，显式提供时优先于 `page*size`。

响应：

~~~json
{"data": [{"id": "batch-1", "type": "process-instance-migration"}], "total": 1, "start": 0, "size": 10}
~~~

### 5.2 批次详情

`GET /service/management/batches/{id}`

- 成功返回 200 与 Batch。
- 不存在返回 404。

### 5.3 批次分片

`GET /service/management/batches/{id}/batch-parts`

- 成功返回 200 与分页结构 `{data,total,start,size}`。
- 批次不存在返回 404。

### 5.4 批次统计

`GET /service/management/batches/{id}/summary`

响应示例：

~~~json
{
  "id": "batch-1",
  "batchId": "batch-1",
  "type": "process-instance-migration",
  "status": "failed",
  "total": 2,
  "completed": 1,
  "failed": 1,
  "inProgress": 0,
  "queued": 0,
  "startTime": "2026-10-28T10:00:00Z",
  "endTime": "2026-10-28T10:00:01Z",
  "tenantId": ""
}
~~~

- `inProgress = total - completed - failed`，负数按 0 处理。
- 统计以分片状态为准，批次不存在返回 404。

### 5.5 分片详情

`GET /service/management/batch-parts/{id}`

- 成功返回 200 与 BatchPart。
- 不存在返回 404。

### 5.6 定义批量迁移

`POST /service/repository/process-definitions/{id}/batch-migrate`

请求：

~~~json
{
  "processInstanceIds": ["pi-1", "pi-2"],
  "activityMappings": {"oldTask": "newTask"}
}
~~~

- 成功返回 **201** 与 Batch JSON。
- 空实例列表返回 400。
- 目标定义不存在或租户不可见返回 404。
- 单个实例迁移失败不会让 HTTP 返回 404/500，而是记录在分片并通过批次 `status=failed` 体现。

原 `POST /service/repository/process-definitions/{id}/migrate` 仍保持同步迁移并返回 204。

## 6. 与 Flowable 的差异

1. **同步执行**：Flowable 通过作业执行器异步处理批次；本实现同步逐实例迁移，
   调用返回时批次已结束，分片不会长期停留在 `queued`。
2. **无 SQL 行**：未映射 ACT_RU_BATCH / ACT_RU_BATCH_PART，只在 JSON 快照中保存；
   RowRepository 唯一状态源模式下重启丢失。
3. **状态集合较小**：只使用 `in-progress`、`completed`、`failed`；
   未实现 Flowable 的挂起、取消、删除批次等操作。
4. **统计端点自定义**：`/summary` 是本仓库补充的聚合视图，Flowable 原生批次 API
   主要通过分片列表和批次字段观察进度。
5. **错误信息为文本**：分片保存 `errorMessage`，未提供异常堆栈端点。
6. **租户过滤在 REST 层**：引擎批次查询不强制租户隔离，列表端点按 `tenantId` 精确过滤。

## 8. 限制与后续

1. 批次与分片只在内存状态和 JSON 快照中保存，尚无 SQL 导入/导出。
2. 同步执行不适合超大实例集合；后续可接入作业执行器拆分为异步分片。
3. 未实现批次挂起、取消、删除、重试失败分片等运维能力。
4. 未对重复的 `processInstanceIds` 去重；调用方应保证输入唯一。
