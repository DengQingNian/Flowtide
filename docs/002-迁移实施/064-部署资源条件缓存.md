# 064 部署资源条件缓存

> 文档编号：002-064  
> 更新日期：2026-10-28  
> 对应计划：012 流程模型仓库；011 REST API 与兼容契约  
> 关联文档：043 部署资源内容类型

## 1. 背景

043 文档在“限制”中记录了部署资源端点未实现 ETag/缓存头的问题：客户端重复读取同一部署资源时始终得到 200 与完整响应体，无法做条件缓存；元数据与原始内容也无法用同一个校验值关联。

本期为部署资源端点补齐 `ETag`、`Last-Modified`、`Cache-Control` 与条件请求（304）支持，闭合 043 的缓存缺口。响应体、`Content-Type`、`Content-Disposition` 以及未知部署/资源的错误状态保持不变。

## 2. 端点与响应头

| 端点 | ETag | Last-Modified | Cache-Control | 条件请求 |
| --- | --- | --- | --- | --- |
| `GET /service/repository/deployments/{id}/resources` | 列表摘要 | 不设置 | `no-cache` | `If-None-Match` |
| `GET /service/repository/deployments/{id}/resources/{name}` | 资源内容摘要 | 部署时间 | `no-cache` | `If-None-Match`、`If-Modified-Since` |
| `GET /service/repository/deployments/{id}/resourcedata/{resourceName}` | 资源内容摘要 | 部署时间 | `no-cache` | `If-None-Match`、`If-Modified-Since` |

- `{name...}` 路由允许资源名包含未编码斜杠；`resourcedata` 使用路径转义（如 `forms%2Fnested.bpmn20.xml`）。两种形式使用相同的摘要算法与条件判断。
- 304 响应不写响应体，保留 `ETag`、`Last-Modified`、`Cache-Control`。
- 200 响应的元数据 JSON、原始字节、`Content-Type`、`Content-Disposition` 均与本期之前一致。

## 3. ETag 语义

### 3.1 单资源

`ETag` 为强校验标签，格式为双引号包裹的小写 SHA-256 十六进制：

~~~text
ETag: "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08"
~~~

- 摘要输入是该资源的**原始字节**，不含资源名、部署 ID、URL、`Content-Type` 等元数据。
- 资源元数据端点与原始内容端点使用同一内容摘要。客户端可把元数据响应得到的 `ETag` 直接用于 `resourcedata` 端点的 `If-None-Match`，反之亦然。
- 部署不可变，因此同一部署内同一资源的 ETag 稳定；相同字节的不同资源（甚至不同部署）会得到相同标签。ETag 的缓存语义仍以完整 URL 为键，跨 URL 复用同一标签不会造成错误命中。
- 编码斜杠资源与普通资源算法一致。

### 3.2 资源列表

列表 ETag 同样是双引号包裹的 SHA-256 十六进制，摘要输入依次为：

1. 部署 ID；
2. 部署时间（UTC，RFC3339Nano）；
3. 按字典序排序后的资源名，每个名称采用“长度前缀 + 冒号 + 原名”编码，避免资源名含分隔符时产生摘要歧义。

因此：

- 资源名返回顺序变化不影响 ETag；
- 部署 ID、部署时间或资源集合任一变化都会改变 ETag；
- 列表 ETag 与单资源 ETag 是不同摘要，不能互换使用；
- 列表不设置 `Last-Modified`，只依据 `If-None-Match` 判断是否可复用缓存。

## 4. Last-Modified 与部署不可变性

`Last-Modified` 取 `GetDeployment` 返回的 `DeployTime`，统一转 UTC 后按 HTTP 日期格式（RFC1123，`http.TimeFormat`）输出：

~~~text
Last-Modified: Wed, 28 Oct 2026 12:00:00 GMT
~~~

前提是**部署不可变**：本仓库不提供修改既有部署资源字节的 API，重新部署会产生新的部署 ID 与新的部署时间。因此部署时间可以作为稳定的最后修改时间。

HTTP 日期只精确到秒，而引擎的 `DeployTime` 可能带纳秒。比较 `If-Modified-Since` 时先把部署时间截断到秒，再与解析结果比较，避免“同一秒内”出现假 200。

## 5. Cache-Control

两个单资源端点与列表端点均返回：

~~~text
Cache-Control: no-cache
~~~

含义是缓存可以保存响应，但每次使用前必须回源校验，不允许直接使用未校验的副本。这里刻意不设置 `max-age`：部署虽然没有独立的资源修改接口，但不同部署、租户隔离与鉴权结果需要由服务端确认，长缓存会把授权/删除等语义交给缓存层。

## 6. 条件请求与 304 规则

### 6.1 If-None-Match

- 支持逗号分隔的多个标签，任意一个与当前 ETag 匹配即视为命中。
- 支持 `*`：当前表示存在即命中（资源不存在仍返回 404，不会因为 `*` 变成 304）。
- 接受弱前缀 `W/` 与 `w/`。`If-None-Match` 按 RFC 7232 使用弱比较，比较时忽略 `W/` 前缀与首尾空白。
- 标签比较包含双引号本身；无引号的非法标签不会误命中。
- 请求头为空或只有空白时视为没有条件。

### 6.2 If-Modified-Since

- 使用 Go 标准库 `http.ParseTime` 解析，接受 RFC1123、RFC850、ANSI C 等 HTTP 日期格式。
- 解析失败时忽略该条件，返回 200，避免因客户端时间格式错误误报 304。
- 部署时间截断到秒后若不晚于请求时间，命中 304；请求时间早于部署时间则返回 200。
- 未来时间按“未修改”处理。

### 6.3 优先级

`If-None-Match` 存在时优先，且不再使用 `If-Modified-Since`。因此：

- ETag 命中 → 304，忽略修改时间；
- ETag 不命中 → 200，即使修改时间条件看起来命中。

这符合 RFC 7232 对两个校验器优先级的约定。

### 6.4 304 响应

命中时：

- 状态码 304；
- 响应体为空（不写元数据 JSON、不写资源字节）；
- 保留 `ETag`、`Last-Modified`（列表无此项）、`Cache-Control`；
- 不修改原有的错误路径：未知部署、部署内不存在的资源仍返回 404，鉴权/租户失败仍由原错误映射决定。

## 7. 与 CDN/反向代理的关系

- `Cache-Control: no-cache` 允许 CDN/代理存储响应，但每次都必须带条件回源。源站返回 304 后，代理可复用已缓存实体，显著减少 BPMN/图片等资源的重复传输。
- 代理必须透传客户端的 `If-None-Match` 与 `If-Modified-Since`，并把源站的 `ETag`、`Last-Modified`、`Cache-Control` 原样返回；若代理自行剥离 `ETag`，条件缓存会退化为每次 200。
- 代理不应把 `no-cache` 改写为 `max-age`，也不应在 304 响应中附加响应体。
- 多个边缘节点若缓存同一 URL，应使用同一套校验器。ETag 只由资源字节计算，不受 `Host`、`X-Forwarded-Proto` 影响，适合跨节点比对；但元数据 JSON 内的绝对 URL 会随 Host 变化，因此缓存键仍应包含完整 URL。
- 共享缓存需要遵守 `Authorization`、租户头等既有鉴权语义；本期未新增 `public`/`private` 指令。

## 10. 限制

1. 元数据端点为了计算内容摘要，会比之前多读取一次资源字节；资源很大时有一定额外开销，但只在本进程内读取，不重复走网络。
2. ETag 仅由资源字节决定：不同资源内容相同会共享标签。按 URL 缓存不会误命中，但若客户端跨 URL 复用标签则不符合缓存规范。
3. 列表 ETag 包含部署时间，重新部署同一批资源会得到新的列表 ETag，这是预期行为。
4. 未实现 `If-Match`、`If-Unmodified-Since`、`If-Range` 与 Range 请求；本期只处理读取侧的条件缓存。
5. 未在资源端点之外（如流程定义 `resourcedata`）推广相同缓存头。
6. 若未来引入“原地修改部署资源”的能力，必须同步改变部署时间或调整 `Last-Modified` 语义，否则会破坏“部署不可变”的前提。
7. 反向代理/网关若不透传条件头或 `ETag`，304 优化不会生效；这属于部署配置问题，不在服务端可控范围内。
8. `Cache-Control` 仅设置为 `no-cache`，未区分 `private`/`public`；共享缓存与鉴权组合仍需部署方按实际安全策略配置。
