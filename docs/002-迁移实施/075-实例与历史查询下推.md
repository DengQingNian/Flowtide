# 075 实例与历史查询下推

> 文档编号：002-075
> 更新日期：2026-10-30
> 对应任务：MySQL 行仓储模式下运行时实例与历史实例查询下推

## 1. 背景与目标

任务查询已在 [062](062-任务查询下推.md) 实现 SQL 下推；运行时流程实例查询与历史流程实例查询仍遍历内存 `e.state.Instances` 与 `e.state.HistoricProcesses` 完成过滤、排序和分页，数据库中的索引无法参与。能力矩阵将其列为集群与容量阶段的未完成项。

本次为两类查询增加 SQL 下推：

- 新增 `flowable.ProcessInstanceQuery` 与 `(*Repository).QueryProcessInstanceIDs`，在 `ACT_RU_EXECUTION` 上执行 COUNT 与分页实例 ID 查询；
- 新增 `flowable.HistoricProcessInstanceQuery` 与 `(*Repository).QueryHistoricProcessInstanceIDs`，在 `ACT_HI_PROCINST` 上执行同类查询；
- 引擎新增 `RuntimeService.QueryProcessInstances` 与 `HistoryService.QueryHistoricProcessInstances` 分页方法：满足安全条件时使用 SQL 返回的实例 ID，再从内存映射 DTO 并做租户校验；不满足条件时回退内存过滤，语义一致；
- SQL 失败直接返回错误，不静默回退；
- REST 的 `GET /runtime/process-instances`、`POST /query/process-instances`、`GET /history/historic-process-instances`、`POST /query/historic-process-instances` 改为按任务查询模式以 1000 条一页循环读取引擎分页结果，后续内存过滤、排序、分页与 DTO 装配保持不变。

既有 `ListProcessInstances` / `ListHistoricProcessInstances` 全量接口保持不变，供指标、迁移核对与索引构建继续使用，零回归。

## 2. 下推触发条件

与任务下推一致（`canPushdownInstanceQuery` / `canPushdownHistoricProcessQuery`）：

1. 引擎配置了 `RowRepository`；
2. 请求上下文租户与引擎默认租户均为空（过滤结构本身不含租户字段）；
3. 运行时查询要求 `hasNonDefaultTenantData` 为假；历史查询另要求 `hasNonDefaultTenantHistory` 为假（内存历史实例全部为默认租户）。

任一条件不满足即整体回退内存路径，行为与改造前一致。

## 3. SQL 形状

### 3.1 运行时实例

```sql
SELECT COUNT(*) FROM ACT_RU_EXECUTION E <WHERE>;

SELECT E.PROC_INST_ID_ FROM ACT_RU_EXECUTION E <WHERE>
ORDER BY E.START_TIME_ ASC, E.PROC_INST_ID_ ASC LIMIT <n> OFFSET <m>;
```

- 实例根行以 `E.PARENT_ID_ IS NULL` 限定：根执行的 `PARENT_ID_` 为外键列，空串在行写入时转换为 SQL NULL；调用活动子实例的根执行同样为 NULL，与内存路径把子实例计入实例列表的语义一致；非根活动的执行行 `PARENT_ID_` 非空，被排除；
- 等值过滤：`E.ID_`、`E.PROC_DEF_ID_`、`E.BUSINESS_KEY_`；
- 挂起过滤：`Suspended *bool` 映射 `E.SUSPENSION_STATE_ = 2 / 1`（与行导出编码一致）；
- 时间过滤：`E.START_TIME_ >= / <=`，下界与上界均含等于，与 REST `matchQueryTime` 边界一致；
- `ProcessDefinitionKey` 通过 `INNER JOIN ACT_RE_PROCDEF P ON P.ID_ = E.PROC_DEF_ID_ AND P.KEY_ = ?` 下推，JOIN 谓词先于 WHERE 占位，保证 PostgreSQL `$n` 编号与文本顺序一致。

### 3.2 历史实例

```sql
SELECT COUNT(*) FROM ACT_HI_PROCINST H <WHERE>;

SELECT H.PROC_INST_ID_ FROM ACT_HI_PROCINST H <WHERE>
ORDER BY H.START_TIME_ ASC, H.PROC_INST_ID_ ASC LIMIT <n> OFFSET <m>;
```

- 等值过滤：`H.PROC_INST_ID_`、`H.PROC_DEF_ID_`、`H.BUSINESS_KEY_`；
- 结束状态：`Finished *bool` 映射 `H.END_TIME_ IS NOT NULL / IS NULL`，与内存 `Ended` 布尔一致；
- 时间过滤：`H.START_TIME_ >= / <=` 与 `H.END_TIME_ >= / <=`（对应 REST 的 `endedAfter` / `endedBefore`）；`END_TIME_` 为空的历史实例不满足任何结束区间，与内存可空时间匹配语义一致；
- 排序键与内存路径一致（开始时间升序、实例 ID 升序）。

### 3.3 错误处理

| 场景 | 运行时实例 | 历史实例 |
| --- | --- | --- |
| 数据库不支持查询 | `ROW-0040` | `ROW-0045` |
| COUNT 查询、扫描或值转换失败 | `ROW-0041` | `ROW-0046` |
| ID 查询失败 | `ROW-0042` | `ROW-0047` |
| ID 扫描或值转换失败 | `ROW-0043` | `ROW-0048` |
| ID 遍历失败 | `ROW-0044` | `ROW-0049` |

错误统一为中文 `api.Error`，不拼接 SQL 文本或参数值。

## 4. 未下推字段与边界

- **租户过滤**：过滤结构不含租户字段；绑定租户或存在多租户数据时整体回退内存。
- **名称、模糊匹配、键集合、删除原因**：`name`、`nameLike`、`businessKeyLike`、`processDefinitionKeyIn`、`deleteReason` 仍由 REST 内存过滤（运行时执行行未持久化 `NAME_`）。
- **GET 历史列表的 `ended`/`finished` 双参数**：两个同义参数同时出现时无法用单一布尔下推，保持内存过滤。
- **REST 复核**：下推字段在 REST 层由既有 `filterQuery*` 再次校验一次，语义幂等；下推路径的时间条件以数据库毫秒精度（`datetime(3)`）为准，亚毫秒边界可能与内存纳秒时间不同，与 062 的取舍一致。
- **总数与可见性**：下推 `total` 来自 SQL；SQL 结果与内存短暂不一致时缺失 ID 被跳过，`total` 可能大于实际条数，与 062 一致。

## 7. 剩余风险

1. 双库真实执行结果待补：MySQL 集成用例已就绪但本轮未运行；PostgreSQL 未验证。
2. 深分页成本：`ACT_RU_EXECUTION`/`ACT_HI_PROCINST` 排序键上的索引沿用官方 Schema，大偏移量 `OFFSET` 未做执行计划评估。
3. 下推查询在 `Engine.read` 读锁内执行，慢查询会拉长写延迟（与 062 相同的取舍）。
4. 调用活动子实例根行的 `PARENT_ID_` 为 NULL 是 Go 行导出的现状；若未来对齐 Java 行拓扑（Java 中子实例根执行 `PARENT_ID_` 非空），实例根判定条件需同步调整。
5. 基线摘要修复仅涉及行尾归一化，`007-history-rest.json` 语义内容与提交内容一致；Java 制品仍只证明其列明场景。
