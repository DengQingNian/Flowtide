# 078 历史活动与历史变量查询下推

> 文档编号：002-078
> 更新日期：2026-10-30
> 对应任务：MySQL 行仓储模式下 ACT_HI_ACTINST 与 ACT_HI_VARINST 查询下推

## 1. 背景与目标

[075](075-实例与历史查询下推.md)、[076](076-租户查询下推.md) 与 [077](077-历史任务查询下推.md) 完成实例、历史实例与历史任务的查询下推；历史活动与历史变量查询仍遍历内存 `e.state.HistoricActivities` / `e.state.HistoricVariables` 完成过滤、排序和分页，数据库索引无法参与。077 的“剩余风险”已把这两类查询列为同模式后续项。

本次按同一模式补齐历史域的最后两类查询：

- 新增 `flowable.HistoricActivityInstanceQuery` 与 `(*Repository).QueryHistoricActivityInstanceIDs`，在 `ACT_HI_ACTINST` 上执行 COUNT 与分页 ID 查询；新增 `flowable.HistoricVariableInstanceQuery` 与 `(*Repository).QueryHistoricVariableInstanceIDs`，在 `ACT_HI_VARINST` 上执行同类查询；
- `api.HistoryService` 新增 `QueryHistoricActivityInstances`、`QueryHistoricVariableInstances` 分页方法：满足安全条件时使用 SQL 返回的 ID，再从内存映射 DTO 并做归属校验；否则回退内存过滤；
- REST 的 `POST /query/historic-activity-instances`、`POST /query/historic-variables`、`GET /history/historic-activity-instances`、`GET /history/historic-variable-instances` 按 1000 条分页循环读取，后续内存过滤、排序、分页与 DTO 装配不变；
- 既有 `ListHistoricActivityInstances`、`ListHistoricVariableInstances` 保持不变，零回归。

## 2. 下推字段与 SQL 形状

### 2.1 历史活动

```sql
SELECT COUNT(*) FROM ACT_HI_ACTINST A <WHERE>;

SELECT A.ID_ FROM ACT_HI_ACTINST A <WHERE>
ORDER BY A.START_TIME_ ASC, A.ID_ ASC LIMIT <n> OFFSET <m>;
```

| Filter 字段 | SQL 条件 |
| --- | --- |
| `ID` | `A.ID_ = ?` |
| `ProcessInstanceID` | `A.PROC_INST_ID_ = ?` |
| `ProcessDefinitionID` | `A.PROC_DEF_ID_ = ?` |
| `ProcessDefinitionKey` | `INNER JOIN ACT_RE_PROCDEF P ON P.ID_ = A.PROC_DEF_ID_ AND P.KEY_ = ?` |
| `ActivityID` / `ActivityName` / `ActivityType` | `A.ACT_ID_` / `A.ACT_NAME_` / `A.ACT_TYPE_ = ?` |
| `Assignee` | `A.ASSIGNEE_ = ?` |
| `TenantID` | `A.TENANT_ID_ = ?` |
| `Finished` | `A.END_TIME_ IS NOT NULL / IS NULL` |
| `StartedAfter/Before` | `A.START_TIME_ >= / <= ?` |
| `FinishedAfter/Before` | `A.END_TIME_ >= / <= ?` |

### 2.2 历史变量

```sql
SELECT COUNT(*) FROM ACT_HI_VARINST V <WHERE>;

SELECT V.ID_ FROM ACT_HI_VARINST V <WHERE>
ORDER BY V.NAME_ ASC, V.ID_ ASC LIMIT <n> OFFSET <m>;
```

| Filter 字段 | SQL 条件 |
| --- | --- |
| `ID` | `V.ID_ = ?` |
| `Name` | `V.NAME_ = ?` |
| `ProcessInstanceID` | `V.PROC_INST_ID_ = ?` |
| `ExecutionID` | `V.EXECUTION_ID_ = ?` |
| `TaskID` | `V.TASK_ID_ = ?` |
| `VariableType` | `V.VAR_TYPE_ = ?` |

### 2.3 边界与错误码

- 时间边界与 075/077 一致：下界与上界均含等于；`END_TIME_` 为空的历史活动不满足任何结束区间；
- 排序键与内存路径一致（历史活动：开始时间升序、ID 升序；历史变量：变量名升序、ID 升序）；
- 错误码：历史活动 `ROW-0055`（数据库不支持查询）、`ROW-0056`（统计/扫描/值转换）、`ROW-0057`（ID 查询）、`ROW-0058`（ID 扫描/转换）、`ROW-0059`（遍历）；历史变量 `ROW-0060`～`ROW-0064` 同构。SQL 失败直接返回错误，不静默回退内存。

## 3. 门禁与内存回退

- **历史活动**（`canPushdownHistoricActivityQuery`）：行仓储已配置；生效租户非空时以 `TENANT_ID_` 等值条件下推（076 语义）；生效租户为空时要求 `hasNonDefaultTenantActivityHistory` 为假——该守卫扫描历史活动 DTO 自身租户与历史实例租户。
- **历史变量**（`canPushdownHistoricVariableQuery`）：`ACT_HI_VARINST` 没有租户列，变量租户由所属流程实例（`PROC_INST_ID_`）或无历史实例的独立任务（`TASK_ID_`）决定。因此仅在“生效租户为空且内存历史实例与历史任务全部为默认租户”时下推（`hasNonDefaultTenantVariableHistory` 同时扫描 `HistoricProcesses` 与 `HistoricTasks` 租户）；任何租户作用域整体回退内存，避免 SQL 把其他租户的变量计入 `total` 并挤占分页。
- 内存回退匹配：历史活动覆盖等值组 + `Finished`（以 `EndTime != nil` 判定）+ 时间边界 + `ProcessDefinitionKey` 经 `findDefinition` 反查；历史变量覆盖等值组（`VariableType` 对应 DTO 的 `Type` 字段）。
- 归属校验 `allowHistoricResource` 在下推与回退两条路径都执行。
- 未下推字段：`activityNameLike`、`variableNameLike` 等模糊匹配仍由 REST 内存过滤。

## 6. 剩余风险

1. `ACT_HI_ACTINST` 深分页成本未做执行计划评估（双库真实执行已通过，见 4.3）。
2. 历史变量无租户列，租户作用域查询永远回退内存；如需下推，需在查询计划中先解析实例集合或扩展 Schema（会破坏官方 DDL 兼容）。
3. 下推查询在 `Engine.read` 读锁内执行，慢查询会拉长写延迟（与 062/075/077 相同取舍）。
4. 历史变量查询忽略请求体 `tenantId`（既有行为）：REST 仅用请求头/认证租户过滤，与历史实例、历史任务、历史活动查询接受 `tenantId` 的契约不一致。本篇保持原契约未改动，补齐需先做原版对照。
5. 下推路径的 `total` 来自 SQL，`data` 会跳过缺失或归属不可见的 ID，二者可能不一致（与 062/075/077 一致）。
