# 004 可插拔状态存储与 SQL 桥接

> 文档编号：002-004  
> 更新日期：2026-10-28  
> 状态：存储接口与 SQL 桥接已实现；按表仓储仍待完成

## 1. 背景

此前引擎直接把状态写入单个 JSON 文件，持久化逻辑与引擎耦合。为接入 PostgreSQL/MySQL，本轮引入 `Store` 接口，并提供三种实现：

| 实现 | 位置 | 用途 |
| --- | --- | --- |
| `FileStore` | `internal/persistence/state` | 现有 JSON 文件，原子替换 |
| `MemoryStore` | `internal/persistence/state` | 单元测试、临时运行 |
| `sqlstate.Store` | `internal/persistence/sqlstate` | 写入 `ACT_GE_BYTEARRAY` |

## 2. 引擎配置

~~~go
engine, err := engine.New(engine.Config{
    StateStore: statestore.NewFile("./data/engine.json"),
})
~~~

- `StateStore` 优先于 `StatePath`。
- 不配置任何存储时，引擎仅使用内存，适用于测试与演示。
- `StatePath` 仍然兼容，内部会自动包装为 `FileStore`。

## 3. Store 接口

~~~go
type Store interface {
    Load(ctx context.Context) ([]byte, error)
    Save(ctx context.Context, data []byte) error
}
~~~

- `Load` 无状态时返回 `nil, nil`。
- `Save` 必须在成功返回后保证数据可读。
- 引擎在命令成功后调用 `Save`；失败则回滚内存状态。
- `Close` 会再保存一次。

## 4. SQL 桥接

`sqlstate.Store` 将完整 JSON 快照写入 Flowable 的 `ACT_GE_BYTEARRAY`：

~~~sql
DELETE FROM ACT_GE_BYTEARRAY WHERE ID_ = 'flowable-go-state';
INSERT INTO ACT_GE_BYTEARRAY (ID_, REV_, NAME_, BYTES_, GENERATED_)
VALUES ('flowable-go-state', 1, 'flowable-go-state', ?, false);
~~~

- MySQL 使用 `?`，PostgreSQL 使用 `$1...$5`。
- `DB` 是自定义接口，生产可传 `SQLDB{DB: sqlDB}`，测试可传内存替身。
- 单条记录容量受 `BYTES_` 类型限制；大规模数据应改为按表仓储。

### 4.1 为什么不是最终方案

这是**过渡桥接**，不是最终关系模型：

1. 整个引擎状态是一个 JSON Blob，无法用 SQL 查询执行/任务。
2. 先删后插，未包事务；并发写可能短暂丢状态。
3. 与 Flowable 的 `ACT_RU_*`/`ACT_HI_*` 表不互通。

## 5. 下一阶段：按表仓储

建议按以下顺序替换：

1. `ACT_RE_DEPLOYMENT`、`ACT_RE_PROCDEF`、`ACT_GE_BYTEARRAY`。
2. `ACT_RU_EXECUTION`、`ACT_RU_TASK`、`ACT_RU_VARIABLE`。
3. `ACT_RU_JOB`、`ACT_RU_EVENT_SUBSCR`、`ACT_RU_IDENTITYLINK`。
4. `ACT_HI_*` 历史表。
5. `ACT_ID_*` 身份表。

每张表需要：

- 行结构体与列映射；
- Insert/Update/Delete/Select 语句；
- 乐观锁 `REV_`；
- 与 `schema.Version` 的启动校验；
- 与 JSON 快照的双读对比测试。
