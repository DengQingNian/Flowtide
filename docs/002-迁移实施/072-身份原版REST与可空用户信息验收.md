# 072 身份原版 REST 与可空用户信息验收

## 1. 范围与原版证据

固定 Java 提交 `f6017e32a4bdd3e59a8881f58b0ee181652d1d9e`，使用原版九个身份控制器、异常处理器、H2 2.4.240 引擎与 Spring 7.0.7 MockMvc，生成 `testdata/compatibility/java/006-identity-rest.json`。52 个独立场景覆盖十九个官方方法：

| 方法 | 路径（前缀 `/service`） | 场景 |
| --- | --- | --- |
| GET / POST | `/identity/users` | 完整对象、排序分页、零数量、属性/成员过滤、模糊模式、创建及冲突 |
| GET / PUT / DELETE | `/identity/users/{id}` | 不存在错误、局部与空更新、显式 null、密码更新效果、删除级联 |
| GET / POST | `/identity/groups` | 完整对象、属性/成员过滤、模糊模式、分页、创建及冲突 |
| GET / PUT / DELETE | `/identity/groups/{id}` | 完整对象、不存在、局部与空更新、显式 null、删除成员关系 |
| POST | `/identity/groups/{id}/members` | 创建 201 及成员对象、重复 409、缺失用户标识 400 |
| DELETE | `/identity/groups/{id}/members/{userId}` | 删除 204、不存在关系 404 |
| GET / POST | `/identity/users/{id}/info` | 键及 URL 列表、创建、重复和缺失字段 |

两个独立 Java 执行的 JSON 结构一致；Java Map 产生的对象键顺序可以不同，因此不将字节摘要不同误记为结构不同。`identity-provenance.json` 保存原版九个控制器字节摘要、本地运行器摘要、独立运行结果及制品摘要。原始样本保留完整正文及二进制 Base64，不能从 Go 实际结果更新预期。

Go 回放严格比较全部响应字段、显式空值、数组顺序、状态码及二进制内容，并独立读取公共身份服务的用户、组、信息、头像、成员关系和密码校验结果。媒体类型按 HTTP 解析后的类型比较，允许 JSON 的 UTF-8 字符集参数，不把合法参数差异当作对象差异。

按用户要求，Java 运行器和重生成脚本只留本地；提交黄金样本、来源记录和 Go 验收代码。

## 2. 用户、组和成员契约

用户及组的官方响应使用独立转换层，输出资源绝对 URL 和显式空值。用户头像存在时才设置 pictureUrl；内部角色、失败次数及密码哈希不直接混入普通读取响应。

用户和组的 PUT 按请求字段是否出现合并属性。未提供的字段保留原值，显式 null 清空对应资料，空对象不再把整组资料清空。用户密码更新验证新密码生效、旧密码失效，资料保持原值。这里仍使用既有公共更新服务，不将顺序请求场景扩展为并发冲突验收。

列表默认按 id/asc，size 为实际条数；零数量返回空页。排序字段使用原版白名单。用户按指定组过滤，组按指定用户过滤，过滤后才计算总量和分页。模糊模式按完整字符串匹配，百分号代表任意字符串，下划线代表一个字符；没有通配符的模式不能退化为包含匹配。

核心成员关系添加/删除接口保留幂等扩展语义，官方 REST 层按原版先检查关系：重复添加返回 409，删除不存在关系返回 404；添加成功返回 201 和成员对象，删除成功返回 204 空正文。

## 3. 用户信息与原版空值键

原版用户信息列表仅包含 key 和 url，值经单个信息资源读取。创建和更新必须提供非 null 值，空字符串与缺省值分开判断。请求体中提供的键必须与路径一致，错误正文按原版输出。

实际 Java 服务在删除用户信息时把值设为 null，仍保留该键；键列表继续列出它，单值读取及再次删除则返回 404。为表达这一行为，内部用户信息改为可空字符串映射，新增公共 `GetUserInfoEntries` 返回包含空值键的独立副本。原有 `GetUserInfo` 继续只返回非空字符串值；`GetUserInfoValue` 把空值视为不存在。

新旧非空值在 JSON 中均为字符串，旧快照可直接解码，不改变快照版本。`TestIdentityInfoNullSnapshot` 验证空值键保存、真实状态存储恢复、旧字符串形式、缺失用户拒绝和返回指针隔离；状态事务克隆逐项复制指针，防止回滚快照共享可写值。

本阶段验证的是内存及 JSON 状态中的身份行为。现有 SQL 行仓储尚未映射用户、组、成员、头像和用户信息表，身份数据的标准行恢复需要后续补齐，不能由流程运行时的双库恢复推导为身份数据恢复通过。

## 4. 头像媒体类型

原版上传处理读取文件部分 Content-Type，额外 mimeType 表单字段不覆盖它。样本故意提交 PNG 文件部分与冲突的 GIF 表单字段，读回实际数据应仍为 PNG。二进制包含零字节及非 UTF-8 字节，Go 直接比较 Base64，不能通过字符串转换掩盖损坏。缺失头像和缺失用户分别保留原版错误语义。
