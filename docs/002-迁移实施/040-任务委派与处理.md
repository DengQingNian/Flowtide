# 040 任务委派与处理

> 文档编号：002-040  
> 更新日期：2026-10-28  
> 对应计划：008 任务、身份与表单；011 REST API 与兼容契约

## 1. 背景

Flowable 任务委派语义：

1. 任务必须先签收（assignee 非空）。
2. `delegate`：原处理人变为 owner，被委托人成为 assignee，`delegationState=PENDING`。
3. `resolve`：由 owner 处理，assignee 恢复为 owner、清空 owner，`delegationState=RESOLVED`。

此前仅实现 delegate 的处理人切换，缺少状态字段与 resolve 动作。

## 2. 模型

`api.Task` 新增 `delegationState`：

| 值 | 含义 |
| --- | --- |
| 空 | 未委派 |
| PENDING | 委派中 |
| RESOLVED | 已处理 |

任务查询 `TaskFilter` 新增 `DelegationState`，支持：

`GET /service/runtime/tasks?delegationState=PENDING`

## 3. 引擎 API

`TaskService` 新增：

```go
Resolve(ctx context.Context, taskID, userID string) error
```

规则：

- 任务不存在 404。
- 实例挂起 409。
- 非 `PENDING` 状态 409。
- 缺少 owner 409。
- `userID` 非空且不等于 owner 返回 403。
- 成功后 assignee=owner、owner 清空、状态 RESOLVED。

`Delegate` 同时写入 `delegationState=PENDING`。

## 4. REST

任务动作：

~~~json
{"action": "delegate", "userId": "bob"}
{"action": "resolve", "userId": "alice"}
~~~

- 成功 204。
- 任务详情/列表响应包含 `delegationState`。
- 支持按 `delegationState` 过滤任务列表。

## 5. 限制

1. 委派不写历史任务专用字段，仅任务日志记录 delegate/resolve。
2. `resolve` 后保留 RESOLVED 状态，任务完成后随任务删除。
3. 未实现 Flowable 的 `delegationState` 查询参数之外的复杂组合过滤。
4. 独立任务与流程任务行为一致。

## 6. 测试

- `internal/engine/task_delegation_test.go`：委派状态、owner/assignee、过滤、非所有者 403、重复处理 409、未签收 409。
- `internal/rest/task_delegation_test.go`：delegate/resolve 动作、状态字段、过滤与错误路径。
- 覆盖率：`internal/engine` 90.8%，`internal/rest` 90.6%。
