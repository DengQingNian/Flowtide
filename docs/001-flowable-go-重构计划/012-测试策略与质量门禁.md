# 012 测试策略与质量门禁

> 文档编号：012  
> 依赖：001 成功标准、003 工程规范  
> 目标读者：QA、全体研发、CI 维护者  
> 硬性要求：**TDD 驱动，行覆盖率 ≥ 0.90**

## 1. 质量目标

| 指标 | 目标 | 门禁 |
| --- | --- | --- |
| 行覆盖率 | ≥ 0.90 | 低于阈值阻断合并 |
| 核心包覆盖率 | ≥ 0.90 | 逐包检查 |
| PR 增量覆盖率 | ≥ 0.95 | diff-cover |
| 单元测试时长 | ≤ 5 分钟 | CI 超时告警 |
| 集成测试时长 | ≤ 15 分钟 | 分片执行 |
| 测试稳定性 |  flaky 率 < 0.5% | 连续 3 次失败隔离 |
| Race | 0 告警 | `-race` 全量 |
| 静态检查 | 0 error | golangci-lint |
| 漏洞 | 0 高危 | govulncheck |

> 0.90 是**行覆盖率**，不是分支覆盖率；但核心判定逻辑（网关、多实例、重试）必须补分支用例，不能靠"跑过一行"凑数。

## 2. TDD 工作流

~~~mermaid
flowchart LR
    A[写失败测试] --> B[最小实现]
    B --> C[重构]
    C --> D[覆盖率检查]
    D --> E[提交]
    E --> A
~~~

规则：

1. **先写测试**：每个公开行为先有失败用例；Bug 修复先写复现用例。
2. **最小实现**：只写让测试通过的最少代码，避免过度设计。
3. **重构**：测试保持绿色；重构不改变行为。
4. **测试命名**：`Test{功能}_{场景}_{期望}`，例如 `TestStartProcess_WhenDefinitionSuspended_ReturnsError`。
5. **一个测试一个断言主题**：允许同一主题多个断言，但失败信息必须可定位。
6. **禁止**提交被 `Skip` 的测试（除非关联 issue 并限时）。
7. **禁止**为覆盖率写无断言测试。

## 3. 测试金字塔

| 层级 | 占比 | 内容 | 运行环境 |
| --- | --- | --- | --- |
| 单元 | ~65% | 纯函数、解析器、求值器、状态机、DTO 转换 | 无 IO，毫秒级 |
| 组件 | ~20% | 命令 + 仓储 + 内存/真实 DB 的切片 | testcontainers 或事务回滚 |
| 集成 | ~10% | 引擎端到端：部署 → 启动 → 任务 → 历史 | PostgreSQL/MySQL |
| 契约/E2E | ~5% | REST 契约、集群、迁移、故障注入 | 容器编排 |

### 3.1 单元测试

- 不启动数据库、不读文件系统、不依赖网络。
- 通过接口注入：`Clock`、`IDGenerator`、`Repository`、`EventDispatcher`。
- 表格驱动 + `t.Run` 子测试。
- 断言优先使用 `go-cmp`，错误使用 `errors.Is`。

~~~go
// TestAgenda_Run_StopsOnError 验证议程遇到错误立即停止。
// @param t 测试上下文
func TestAgenda_Run_StopsOnError(t *testing.T) {
    executed := 0
    agenda := NewDefaultAgenda(100)
    agenda.Schedule(OperationFunc(func(ctx *CommandContext) error {
        executed++
        return nil
    }))
    agenda.Schedule(OperationFunc(func(ctx *CommandContext) error {
        executed++
        return ErrAgendaOverflow
    }))
    agenda.Schedule(OperationFunc(func(ctx *CommandContext) error {
        executed++
        return nil
    }))

    err := agenda.Run(&CommandContext{})
    if !errors.Is(err, ErrAgendaOverflow) {
        t.Fatalf("期望 ErrAgendaOverflow，实际 %v", err)
    }
    if executed != 2 {
        t.Fatalf("期望执行 2 个操作，实际 %d", executed)
    }
}
~~~

### 3.2 组件测试

- 使用真实数据库，但每个测试在事务中执行并回滚，保证隔离与速度。
- 引擎构造使用测试配置：固定时钟、递增 ID、关闭异步执行器。
- 数据库通过 `testcontainers-go` 启动一次，测试包共享；每个测试用唯一 schema/租户。

~~~go
// newTestEngine 创建使用真实数据库的测试引擎。
// @param t 测试上下文
// @return 引擎实例
// @return 清理函数
func newTestEngine(t *testing.T) (Engine, func()) { /* ... */ }
~~~

### 3.3 集成测试

- 完整链路：HTTP → Service → Command → DB → 历史/作业。
- 每个场景独立数据库或独立租户。
- 异步作业使用手动触发模式（`RunOnce`），避免等待。
- 定时器使用假时钟推进。

### 3.4 契约测试

- 从官方 OpenAPI 生成路径清单，断言 Handler 覆盖。
- 响应体用 `kin-openapi` 校验 schema。
- Java 回放对比（见 011 文档），差异白名单化。

## 4. 覆盖率工程

### 4.1 统计口径

- 工具：`go test -covermode=atomic -coverprofile=coverage.out ./...`。
- 合并多包：`go tool covdata` 或 `gocovmerge`。
- 排除：
  - `cmd/`（入口装配）
  - 生成的 OpenAPI DTO
  - `test/testutil`、`test/fixtures`
  - `**/mock_*.go`
  - 内嵌 SQL/资源文件（非 Go 代码）
- 排除必须登记在 `.coverignore`，由 `covergate` 工具读取并输出报告。

### 4.2 门禁命令

~~~bash
go test -race -covermode=atomic -coverprofile=coverage.out ./...
go run ./tools/covergate   -profile coverage.out   -exclude .coverignore   -total 0.90   -per-package 0.85   -critical 0.95
~~~

规则：

- 总覆盖率 < 0.90 → 失败。
- 任一非排除包 < 0.85 → 失败（需架构组豁免）。
- 关键包（`internal/runtime`、`internal/persistence`、`internal/expression`、`internal/job`）< 0.95 → 失败。
- 新增代码覆盖率 < 0.95 → 失败。
- 覆盖率报告作为 CI 制品保留 30 天。

### 4.3 提高可测性的设计约束

| 约束 | 目的 |
| --- | --- |
| 时钟注入 | 定时器/超时可测 |
| ID 生成注入 | 断言稳定 |
| 仓储接口化 | 单元测试可替换 |
| 行为纯函数化 | 网关/条件易测 |
| 禁止包级单例 | 测试可并行 |
| 错误码稳定 | 断言不依赖文案 |
| 小函数 + 显式依赖 | 分支易覆盖 |

## 5. 测试数据与夹具

### 5.1 BPMN 夹具

- 来源：Flowable 参考仓库的 1,725 个 `*.bpmn20.xml`（Apache-2.0，保留版权声明）。
- 目录：`test/fixtures/bpmn/{category}/{name}.bpmn20.xml`。
- 每个夹具配套 `{name}.golden.json`：解析后的模型摘要、执行路径、历史快照。
- 大文件裁剪：仅保留与本项目相关的元素，避免仓库膨胀。

### 5.2 黄金文件

- 生成：`go test ./... -update`。
- 审核：黄金文件变更必须在 PR 中说明原因，Reviewer 重点检查。
- 对比：忽略时间、ID、数据库生成列；其余字段严格相等。
- 存储：JSON，字段排序稳定，便于 diff。

### 5.3 测试数据隔离

- 每个测试使用唯一 `tenantId` 或独立 schema。
- 禁止依赖执行顺序；`t.Parallel()` 默认开启（除共享容器初始化）。
- 测试结束清理数据；容器测试整体回滚/销毁。

## 6. 模糊测试与属性测试

| 目标 | 类型 | 断言 |
| --- | --- | --- |
| BPMN XML 解析 | `FuzzParse` | 不 panic、错误可读、资源受限 |
| 表达式编译/求值 | `FuzzCompile`、`FuzzEval` | 不 panic、超时可控 |
| JSON 变量 | `FuzzJSON` | 不 panic、类型正确 |
| 查询构造器 | `FuzzQuery` | 不生成非法 SQL、不注入 |
| 定时器表达式 | `FuzzTimer` | 不 panic、结果单调 |

属性测试示例：

- 任意合法 BPMN：解析 → 导出 → 再解析，模型等价。
- 任意变量：编码 → 解码，值等价（浮点 NaN 除外）。
- 任意分页：`offset+size` 不越界、总数一致。

## 7. 并发与故障测试

| 场景 | 方法 | 断言 |
| --- | --- | --- |
| 并发签收 | 100 goroutine | 仅 1 成功，其余 409 |
| 并发完成 | 同一任务多次 complete | 仅 1 次推进 |
| 乐观锁 | 两个事务更新同一执行 | 一方冲突，数据一致 |
| 作业抢占 | 双节点同时扫描 | 无重复执行 |
| 节点崩溃 | kill -9 执行中节点 | 锁过期后恢复 |
| 数据库断连 | 中途关闭连接 | 事务回滚、可重试 |
| 慢查询 | 注入延迟 | 超时、指标、告警 |

- 使用 `go.uber.org/goleak` 检查 goroutine 泄漏。
- 使用 `-count=10` 跑并发敏感测试，捕获偶发失败。
- 故障注入通过 `testutil.FaultyDB` 包装 `database/sql` 驱动。

## 8. 基准与性能测试

### 8.1 微基准

~~~go
// BenchmarkExpressionEval 基准测试简单条件表达式求值。
// @param b 基准上下文
func BenchmarkExpressionEval(b *testing.B) {
    expr, _ := Compile("${amount > 100 && approved}")
    env := &Env{Vars: map[string]any{"amount": int64(200), "approved": true}}
    b.ResetTimer()
    for i := 0; i < b.N; i++ {
        _, _ = expr.Eval(context.Background(), env)
    }
}
~~~

### 8.2 端到端基准

| 场景 | 数据量 | 指标 |
| --- | --- | --- |
| 启动实例 | 1 万 | p50/p95/p99、TPS |
| 完成任务 | 1 万 | p95、TPS |
| 待办查询 | 100 万任务 | p95 |
| 历史轨迹 | 100 万活动 | p95 |
| 作业吞吐 | 10 万积压 | 作业/秒 |
| 定时器精度 | 1 万定时器 | 延迟 p99 |

- 工具：`k6`（HTTP）、`testing.B`（内核）。
- 基线：每次合并到 main 记录；PR 回退 > 10% 失败（可 label 豁免）。
- 环境：固定 4c8g、PostgreSQL 16、SSD；结果写入 `benchmarks/`。

## 9. 静态检查与安全

| 工具 | 作用 | 门禁 |
| --- | --- | --- |
| `gofmt`/`goimports` | 格式 | 必须 |
| `go vet` | 基础缺陷 | 0 |
| `staticcheck` | 深度静态分析 | 0 |
| `golangci-lint` | 聚合 lint | 0 error |
| `doccheck` | 中文注释/@param/@return | 0 缺失 |
| `gocyclo` | 圈复杂度 | > 15 告警，> 25 失败 |
| `govulncheck` | 依赖漏洞 | 0 高危 |
| `gosec` | 安全模式 | 0 高危 |
| `misspell` | 拼写 | 0（中文注释除外） |

自定义 `doccheck` 规则：

- 函数必须有中文注释。
- 参数数量与 `@param` 数量一致。
- 返回值数量与 `@return` 数量一致。
- 导出符号必须有注释。
- 注释不得为英文（允许专有名词）。

## 10. CI 流水线

~~~mermaid
flowchart LR
    A[fmt + vet] --> B[lint + doccheck]
    B --> C[unit -race]
    C --> D[covergate 0.90]
    D --> E[component PG/MySQL]
    E --> F[integration + conformance]
    F --> G[contract OpenAPI]
    G --> H[benchmark compare]
    H --> I[govulncheck/gosec]
    I --> J[build binaries/images]
~~~

- PR：A–D + 快速组件测试（≤ 10 分钟）。
- main：全量（≤ 40 分钟），并行分片。
- nightly：并发/故障/模糊/Java 回放/性能。
- 失败策略：质量门禁失败阻断合并；nightly 失败创建 issue 并通知。

## 11. 缺陷与回归

| 严重级别 | 响应 | 要求 |
| --- | --- | --- |
| P0 数据损坏/不可用 | 立即 | 热修复 + 复盘 + 回归用例 |
| P1 核心流程错误 | 24h | 修复 + 回归用例 |
| P2 功能缺陷 | 迭代内 | 修复 + 用例 |
| P3 体验/文档 | 排期 | 可合并到常规 |

- 每个 Bug 修复必须附带**先失败后通过**的测试。
- 回归用例放入对应模块，不集中到 `regression_test.go`。
- 线上问题需记录：现象、根因、影响范围、修复、预防。

## 12. 迁移与兼容测试

- 使用 Flowable 8.x 初始化的数据库 fixture，验证 Go 引擎可启动、可读写。
- 用同一 BPMN + 操作序列分别跑 Java/Go，比较：
  - 活动路径（`ACT_HI_ACTINST`）
  - 任务与变量终态
  - 作业数量与类型
  - 历史行数与关键字段
- 差异分类：允许（ID/时间/顺序）、待修（语义）、阻塞（数据不一致）。
- 迁移工具测试：Java 序列化变量、Java 委托、未知元素、租户、定时器。

## 13. 完成定义（Definition of Done）

一个功能只有满足以下条件才算完成：

- [ ] 有设计说明或更新了对应文档。
- [ ] 先写测试，覆盖正常/边界/错误路径。
- [ ] 行覆盖率达标，新增代码 ≥ 0.95。
- [ ] `go test -race`、lint、doccheck 通过。
- [ ] 有集成测试或说明为何不需要。
- [ ] 错误码、日志、指标齐备。
- [ ] 文档、示例、迁移说明更新。
- [ ] Code Review 通过，无未决评论。
- [ ] 在 `main` 上 CI 全绿。

## 14. 验收清单

- [ ] 总行覆盖率 ≥ 0.90，关键包 ≥ 0.95。
- [ ] CI 可在 40 分钟内完成全量回归。
- [ ] 1,725 个 BPMN 夹具中 ≥ 90% 可执行/可解析。
- [ ] 并发、故障、模糊测试纳入 nightly。
- [ ] 性能基线可比较，回退可阻断。
- [ ] 迁移兼容测试覆盖数据/语义/接口三层。
- [ ] 所有 Bug 修复有回归用例。
